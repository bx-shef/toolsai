# Памятка агенту: shef.toolsai

Модуль коробочного Битрикс24: свой ИИ-движок для Копилота (категории `audio`
и `text`), учёт расхода с месячной квотой и анализ сделок. Опирается на
`shef.options` и `shef.problems` и сделан по их канону — сборка, тесты,
раскладка, решения, ловушки. Если здесь чего-то не хватает, смотрите
[CLAUDE.md shef.options](https://github.com/bx-shef/options/blob/main/CLAUDE.md):
всё, что там сказано про устройство модуля линейки, верно и здесь.

Проверка перед сдачей — всегда `./build.sh --check`, ровно это же гоняет CI.

**Как работа попадает в `main`** — [docs/agent-rules.md](docs/agent-rules.md):
только через PR; `/code-review` на каждый PR, а на изменения поведения,
безопасности, денег, установщика и CI — панель из пяти проверяющих
(документация, инженер, QA, безопасность, CTO); чек-лист перед мержем и после;
рабочая дисциплина (замер вместо «должно», тест краснеет при поломке, никогда
`git checkout --`) и то, что необратимо и решается владельцем.

**Фундамент — [docs/00-research.md](docs/00-research.md).** Почти каждое
решение в модуле продиктовано конкретной строкой ядра, и «упростить» обычно
означает «сломать». Прочитать до правки архитектуры.

Тесты лежат в `tests/`, гоняются как обычные скрипты. Обвязка
`tests/assert.php` общая с линейкой: сравнение строгое, warning и notice —
провал. Ядро подменяется заглушками `tests/stub/bitrix.php` (плюс
`psr.php`, `options.php` — API страницы настроек shef.options 3.x), подставные
транспорт, журнал, квота и провайдер — `tests/stub/fakes.php`. Классы модуля
подключаются **настоящие** автозагрузкой `tests/stub/autoload.php`.

**Навыки — двух видов.** Навыки линейки — копия из
[bx-shef/options](https://github.com/bx-shef/options), раскладывает
`sync.sh --to`, там же их и правят; задача `Skills` в CI сверяет копию с
источником. Локальный — `shef-new-ai-provider` (новый провайдер, вызов LLM
из своего модуля с учётом расхода): источник здесь, после правки —
`.claude/skills/sync.sh --local`.

**Примеры в `examples/` запускаются, а не читаются** — `contract.php`
(контракт движка целиком) и `quota.php`. `php examples/x.php` — на
заглушках, `DOCUMENT_ROOT=/var/www/portal php examples/x.php` — на портале.

**Приёмка на живой коробке — Docker.** `docker/` — стенд (apache + mod_php
как BitrixVM, MySQL, заглушка OpenAI-совместимого API, тестовый звонок),
[docs/agent-docker-test.md](docs/agent-docker-test.md) — готовый промпт для
ИИ-агента с этапами и бланком отчёта.

## Опорные точки

**Путь запроса.** Ядро (`ThirdParty::completions()`) POST-ит задание на
`completions_url` -> заглушка `/bitrix/tools/shef_toolsai_completions.php` ->
`endpoint/completions.php` -> `Completion\Endpoint::handle()` решает статус ->
ответ 202 и закрытие соединения -> `Completion\Dispatcher::dispatch()`:
журнал (`start`), квота, провайдер, журнал (`finish`), колбэк
(`Completion\Callback`) на URL из запроса.

**Два статуса на одном адресе.** GET — ровно 200 (проверка при регистрации
движка), POST — ровно **202**. Сравнение строгое; 200 на POST ядро считает
сбоем.

**Токен — в адресе, не в заголовке.** Запрос шлёт ядро, своих заголовков оно
не добавляет; единственное, что задаём мы, — `completions_url`. Поэтому
`Config::getCompletionsUrl()` = внешний адрес + заглушка + `?token=<64 hex>`.
Токен генерирует `Main\Setup::ensureToken()`, хранится в `SYS_token`, на
странице настроек не показывается. Токен оседает в access-логах: ротация —
`Setup::rotateToken()` (кнопка на странице расхода, `ROTATE_TOKEN=1
cli/setup.php`).

**Колбэк — только на хост портала** (`Security\CallbackGuard`): хосты из
внешнего адреса и `ai::public_url`. Путь колбэка не проверяем и не строим —
маршруты ядро держит у себя. Без `hash` в колбэке — 400 `no_hash`.

**Транспорт не ходит по редиректам** (`Http\BitrixTransport`): адрес
проверяется до запроса, а редирект с разрешённого хоста увёл бы запрос во
внутреннюю сеть. Запись звонка (`prompt.file`, тоже из тела запроса)
качается с приватными адресами только для хоста портала; редиректы
`AsrProvider` проходит сам, проверяя каждый шаг.

**Диспетчер не бросает.** Любой сбой — база, журнал, квота — отдаёт ядру
`internal_error`: задание без колбэка висит у ядра до ttl. Колбэк
повторяется при 0/429/5xx. Запись «в работе» старше
`Ledger::STALE_AFTER` повтор задания забирает себе.

**Внешний адрес портала** — `DEF_publicurl`, пусто — `ai::public_url`. Пусто
оба — движки не регистрируются: `UrlManager::getHostUrl()` за прокси даёт
внутренний адрес, и колбэк уходит в никуда.

**Регистрация движка — только `\Bitrix\AI\ThirdParty\Manager::register()`**
(`Engine\Registrar`). Он сбрасывает кеш с приватным ключом;
`ThirdPartyRegisterService` напрямую — запрещено. Адрес поменялся —
`unregister` + `register` (пара код+категория уникальна).

**Включение — `Main\Setup::run()`**: токен, заглушки, `AI_IGNORE_BAAS`,
движки, агент — и отчёт о выборе движка в настройках ИИ (`selected *`,
только чтение). Движки `audio` и `text` — одним прогоном: audio виден CRM
лишь при text-движке (`ThirdParty::hasQuality()`), и отчёт не считает audio
готовым без text. Идемпотентно. Зовут установщик, кнопка «Проверить и
включить» на странице расхода и `cli/setup.php`. После каждого обновления
платформы — прогнать.

**Выбор движка в настройках ИИ — только со страницы настроек модуля.** CRM
берёт движок строго по коду из настройки ИИ (`abstractoperation.php:684-697`,
без фолбэка). Пишет туда `Setup::selectEngines()`, и зовёт его только
ссылка «Выбрать движок модуля» на вкладке «Движок» (`options_conf.php`:
администратор + `check_bitrix_sessid()`, потом `LocalRedirect`; своей формы
нет — `options.php` канонический и не правится). Заменяет и чужой выбор —
это явное действие администратора; выбирает только зарегистрированные
движки, audio — только при text. При удалении, если в настройке всё ещё
наш код: выбирал модуль (`SYS_selected_*`) — возвращается прежнее значение
(`SYS_previous_*`), выбрал администратор руками — очищается.
Установщик, `run()` и CLI выбор только показывают.

**Журнал расхода** — `shef_toolsai_usage`, уникальный индекс по `JOB_HASH`.
Запись в два шага: `start()` с оценкой (статус `PROCESSING`) до провайдера,
`finish()` после. Повтор задания отсекает индекс, а не проверка «было ли».
Квота: `Quota\Meter` суммирует `SUCCESS` и свежие (2 ч) `PROCESSING`;
диспетчер после `start()` спрашивает `Balance::isExceeded()`.

**Деньги — в микро-единицах, строкой.** `Main\OptionParser::micro()` не
знает float: `0.1` — ровно 100 000. Цены LLM — за миллион токенов, то есть
токен × цена даёт микро ровно.

**Провайдер выбирается на каждый запрос** (`Container::getProvider()`):
смена заглушки на OpenAI не требует перерегистрации движка. HTTP — только
через `Http\TransportInterface` — ради тестов без сети.

**Публичные страницы пишутся, а не копируются** (`Main\PublicPage`, канон —
`AdminPage` shef.problems): путь в заглушке — туда, где модуль стоит на
самом деле; удаляется только своя. `installDir` пуст.

**Логи — через shef.problems** (`Container::getLogger()`): тип «Продажи и
CRM», уровень Warning. Нет shef.problems — `null`, учёт расхода важнее лога.

**Агент** — `Agent\DealHealthAgent`, по канону shef-new-agent: `Pid` из
shef.options с проверкой каталога группы, `FixUser` (модуль shef.options
подключается до слова `class`), `finally`. Работает только при
`DEAL_enabled = Y` и выбранных направлениях; ручной прогон —
`cli/deal-health.php`.

**Установщик** — `install/index.php`, канон shef.problems (UTF-8, версии,
`savedata`, `getModuleDir()`) плюс таблицы, заглушки, `InstallEngine()` /
`UnInstallEngine()`. В `UnInstallEngine()` на классы модуля не опираемся:
коды движков и группа блокировок — литералами.

## Решения владельца

Это решения, а не баги. Не переигрывать без просьбы.

**Настройки ИИ портала модуль меняет только со своей страницы настроек**
(владелец, 2026-09-29): «Можно — но делать это из страницы настроек модуля
в админке Б24». Установщик, «Проверить и включить» и `cli/setup.php` выбор
движка не пишут, только показывают.

**База — кит `shef-toolsai-kit`**, доведённый до канона линейки: модуль в
корне репозитория (а не `module/` + `endpoint/` + `tools/`), `lib/`
строчными, установка из `/bitrix/modules` (кит клал в `/local/modules` —
работает и там), тесты по обвязке линейки вместо PHPUnit-каркаса.

**Провайдеры — OpenAI-совместимые.** Один протокол закрывает OpenAI, свои
whisper-серверы, vLLM, LocalAI, Ollama и прокси; меняется настройкой, а не
кодом. Другой протокол — навык `shef-new-ai-provider`.

**Заглушка по умолчанию.** Платный провайдер включается осознанно, после
прогона пути на `echo` — так завещал кит, и это дешевле любой отладки.

**Эндпоинт — в `/bitrix/tools`, а не в `/local/ai`.** `/bitrix/tools`
публичен на любом портале, `/local` модуль не создаёт.

**Журнал расхода — данные, но уходит вместе с модулем** без `savedata = Y` —
как настройки в линейке. Кит оставлял таблицу навсегда; в линейке «поставить
начисто» важнее, а сохранить можно через `savedata`.

**Обход BaaS снимается при удалении, только если включал его модуль**
(`SYS_baasset`).

**Анализ сделок — по описаниям дел, а не по резюме Копилота.** Где ядро
хранит резюме, зависит от версии crm; опора на это — ещё одна точка
хрупкости. Описания дел читаются из `ActivityTable`.

**Эскалация — комментарий + дело старшему.** Без чата и без смены
ответственного.

**`shef.insync` не нужен.** HTTP-клиент провайдеров свой и маленький
(`Provider\OpenAi\Client`): тянуть модуль синхронизаций ради одного
`AConnector` — лишняя зависимость в установке.

## Ловушки, за которые заплачено

**Подпись заголовком не доедет.** Кит защищал эндпоинт `X-Shef-Signature` —
ядро этот заголовок не шлёт, эндпоинт отвечал бы 403 на каждый настоящий
запрос. Всё, что должен знать эндпоинт, — в `completions_url`.

**200 вместо 202 — тихий сбой.** POST ушёл, выглядит успешным, а задание
ядро пометило ошибкой. Держит `tests/endpoint_test.php`.

**Пустой текст — не успех.** Пустая транскрипция обрывает цепочку ядра
молча (`canProceedToNextStep()`); `Callback::success()` превращает её в
ошибку `empty_result`.

**`canSpend(0)` при перерасходе — true.** Остаток не бывает отрицательным,
поэтому «хватит ли на 0» при перерасходе отвечало «да». Диспетчер
спрашивает `isExceeded()`. Нашёл `tests/dispatcher_test.php`.

**Провайдер повторяет ключ в тексте ошибки** («Incorrect API key sk-…»), а
текст уходит в журнал, лог и карточку. `OpenAi\Client` маскирует.

**apache + mod_php не умеет `fastcgi_finish_request()`.** Эндпоинт отдаёт
`Content-Length` и `Connection: close` и сбрасывает буфер; держит ли nginx
соединение до конца обработки — проверяется на стенде (время ответа POST,
[portal-check.md](docs/portal-check.md), шаг C). Если держит — переносить
обработку в очередь (агент/cron), а не удлинять таймаут.

**Классы с заглавными в `lib/`** (так было в ките) — на Linux ядро их не
находит. `check_lowercase` и `tests/autoload_test.php`.

**Проверяй артефакт, а не свой диф** — как в shef.options.

## Известные шероховатости

Не трогать заодно — отдельной задачей, с проверкой на портале.

* `cli/core-api-guard.php`, `ai-call-autostart-diag.php`,
  `ai-limits-report.php` — перенесены из кита как есть: стиль (пробелы,
  K&R), читают приватные константы ядра через Reflection. Это диагностика,
  не рантайм.
* Поля ядра, на которые модуль опирается без теста (нужна коробка):
  `EngineTable.COMPLETIONS_URL`, `ActivityBindingTable`,
  `DealStageHistoryTable`, `Timeline\CommentEntry::create()`,
  `Activity\Entity\ToDo`; в 1.0.1 добавились `HttpClient::getHeaders()`
  (Location при выключенных редиректах), `setPrivateIp(false)` на GET,
  `SqlHelper::getCurrentDateTimeFunction()` / `convertToDbDateTime()` и
  `Connection::getAffectedRowsCount()` (перехват брошенной записи журнала),
  константа `BX_SECURITY_SESSION_VIRTUAL`; `\Bitrix\AI\Tuning\Manager`
  (`getItem()`, `save()`, `$item->setValue()`) и константы
  `EventHandler::SETTINGS_FILL_ITEM_FROM_CALL_ENGINE_*_CODE` — из
  обновлённого кита. Сверяются на стенде —
  [agent-docker-test.md](docs/agent-docker-test.md), этап 2.
* Одно задание распознавания на дело (гейт 13 в `docs/00-research.md`):
  каждый наш колбэк ошибки — `quota_exceeded`, `provider_*`,
  `file_download` — это звонок, который автоматически уже не распознается.
  Своей очереди повторов у модуля нет; решение — отдельной задачей, после
  разведки штатной очереди ядра:
  [agent-queue-research.md](docs/agent-queue-research.md).
* Лимита частоты на эндпоинте нет — держатель токена ограничен только
  месячной квотой. Ротация токена есть, ограничение параллельных заданий —
  отдельной задачей.
* Ключ API на странице настроек — обычное текстовое поле (`Options\Text`):
  виден администратору открытым текстом. Поля-пароля в shef.options нет.
* Расход анализа сделки пишется после ответа модели: сбой между ответом и
  записью оставит трату без следа (для Копилота журнал пишется до провайдера).
* Схема таблиц — MySQL (`CREATE TABLE … AUTO_INCREMENT`), как у коробки.
  Коробка на PostgreSQL не проверялась.
* Оценка стоимости распознавания до скачивания — час записи: при почти
  исчерпанной квоте короткий звонок получит отказ. Уточнять — по
  длительности из статистики телефонии.
* Анализ сделок не учитывает переписку (открытые линии, почту) — только
  дела и звонки.

## Вопросы владельцу

Панель 2026-09-29 (CTO) отметила решения, которые принял агент, а по
[правилам](docs/agent-rules.md) §5.8 они принадлежат владельцу. До ответа
действует то, что записано выше, но это не подтверждено:

* установщик **сам** включает `crm::AI_IGNORE_BAAS`, регистрирует движки
  (если задан адрес) и ставит агент — или установка и включение должны быть
  раздельны (только по кнопке «Проверить и включить»)?
* обход BaaS меняет коммерческое поведение платформы — допустимо ли это по
  лицензии и поддержке?
* журнал расхода (деньги клиента) уходит при удалении без `savedata = Y`;
* «Решения владельца» выше записаны агентом при сборке 1.0.0 из кита:
  OpenAI-совместимые провайдеры, заглушка по умолчанию, эндпоинт в
  `/bitrix/tools`, свой HTTP-клиент вместо shef.insync, анализ сделок по
  описаниям дел, эскалация записью в CRM клиента — подтвердить;
