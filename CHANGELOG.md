# Изменения

## 1.1.0 — 2026-10-03

Профили анализа сделок (#29) — как скрипты речевой аналитики CRM. Раньше
у анализа были одни настройки и один промпт на все направления.

* Таблица `shef_toolsai_deal_profile` (`Deal\Model\DealProfileTable`):
  название, включён, сортировка, направление, типы клиента (коды речевой
  аналитики, пусто — любой), свой промпт (пусто — общий), «зависла через N
  дней», повтор через N дней, нижняя и верхняя границы риска, старший.
* Подбор профиля к сделке — `Deal\ProfilePicker` (чистая функция): тип
  клиента — штатный `ClientTypeResolver` по контакту или компании; профиль с
  типом главнее «любого», дальше SORT и ID. Нет профиля — модель не зовём.
* Шкала — `Deal\RiskScale` (чистая функция): риск от нижней границы — дело
  ответственному, если у сделки нет запланированных дел; от верхней и при
  `needSenior` — комментарий и дело старшему; один человек — одно дело.
  Повтор — не чаще срока профиля (`MANAGER_TODO_AT`, `ESCALATED_AT`).
* Страница «ИИ: профили анализа сделок»
  (`/bitrix/admin/shef_toolsai_deal_profiles.php`), пункт в меню.
* Вкладка «Анализ сделок»: только включение, лимит за прогон и ссылка на
  профили. `DEAL_categories`, `DEAL_threshold`, `DEAL_senior`,
  `DEAL_reanalyzedays`, `DEAL_idledays` устарели: `Deal\ProfileMigration`
  один раз переносит их в профили (по одному на направление, обе границы =
  порог, промпт общий). Переход идемпотентный: кнопка «Проверить и
  включить», агент, страница профилей.
* В таблицу проверок дописываются столбцы `MANAGER_TODO_AT`, `PROFILE_ID`.
* В сводке для модели — число запланированных (незавершённых) дел.

## 1.0.6 — 2026-10-03

Боевой портал (#11), после 1.0.5: оценка звонка снова «не JSON» (5870 симв.,
stop, Syntax error). Ручной повтор с тем же промптом показал скелет ответа
(текст разговора замаскирован): кавычки и экранирование в порядке, но
скобок «{» 28, а «}» 27 — модель не закрыла `call_review`, и итог с
рекомендациями оказались внутри него.

* Промпт оценки просит плоскую форму: `criteria`, `overall_summary`,
  `recommendations` — три ключа верхнего уровня, пример тоже плоский.
  Вложенную форму CRM (`call_review.criteria`) собирает
  `CopilotPrompt::normalizeScoring()`; принимает обе формы, итог и
  рекомендации ищет и в корне, и внутри `call_review`.
* `Llm::repairJson()` дописывает скобки, оставшиеся открытыми к концу ответа,
  в нужном порядке; внутри строк скобки не считаются, оборванную строку не
  трогает. Ответ, обрезанный по лимиту (`finish_reason length`), не чинится
  вовсе — только повтор: ему не хватает данных, а не скобки.
* В ошибке «не JSON-объект» — подсчёт скобок вне строк
  (`Llm::describeBrackets()`: «скобки { 28/27, [ 1/1»), без текста ответа.

## 1.0.5 — 2026-10-03

Боевой портал (#11), после 1.0.4: оценка звонка снова «не JSON», но уже с
причиной — «попыток 2; последний ответ: 6484 симв., finish_reason stop».
Ответ не обрезан: модель вернула объект с синтаксической ошибкой. Ручной
повтор с короткой расшифровкой разбирался — там цитаты были «ёлочками».

* `Llm::repairJson()`: если объект из ответа не разобрался — починка
  типичных огрехов внутри строк: прямая кавычка цитаты экранируется (кавычка
  закрывает строку, только если за ней `:` `}` `]` конец или `,` с новым
  значением), сырые переносы строк, табы и прочие управляющие символы.
  Структуру не угадываем — что не починилось, отвергает `json_decode`.
* В ошибке — ещё и тип ошибки разбора (`json_last_error_msg()`), без текста.
* Промпт оценки описывает формат ответа точно: один объект по RFC 8259 без
  текста вокруг, структура с типами, пример правильного ответа, правила JSON
  (двойные кавычки, без `"` внутри строк — цитаты «ёлочками», без переносов,
  без висячих запятых, ровно эти ключи), число критериев — ровно столько,
  сколько в скрипте.

## 1.0.4 — 2026-10-03

Боевой портал (#11): оценка звонка по скрипту на DeepSeek упала с «Модель
вернула не JSON-объект», в журнале — 0 токенов. Ручной повтор с тем же
промптом дал валидный JSON, но на пределе умолчания провайдера: 2955
токенов ответа (из них 1060 — рассуждения) при 26 критериях скрипта и
короткой расшифровке.

* Оценка звонка — `max_tokens` 8192: умолчание DeepSeek (~4K) обрезало JSON
  посередине на настоящем звонке. Не выше потолка выхода `deepseek-chat`
  (8K): больше потолка модели провайдер отвечает 400 на каждый запрос, и
  оценка не прошла бы ни разу (в первой редакции стояло 16000). Свой
  потолок — `max_tokens` в «Доп. параметрах модели текста»: он сильнее
  умолчания модуля. Оценка расхода до вызова для оценки звонка — 4000
  токенов ответа, а не 2000.
* `completeJsonObject()`: негодный ответ (пустой, обрезанный, не объект) —
  один повтор; обе попытки — в расход. Ошибка называет форму ответа
  (длина, `finish_reason`), но не его текст — в нём персональные данные.
* Сбой провайдера с уже оплаченным ответом пишется в журнал расхода с
  ценой (`ProviderException::spentUnits/spentMicro`): раньше диспетчер
  записывал 0, и квота не видела этих денег.

## 1.0.2 — 2026-10-03

* Модели уходил **сырой шаблон** промпта Копилота вместо готового текста.
  Ядро присылает стороннему движку оба: `prompt` — уже собранный через
  `Formatter` с маркерами (расшифровка, язык), и `payload_prompt_text` —
  шаблон с `{маркерами}` и `@switch/@case`. Модуль брал шаблон первым: на
  боевом портале резюме звонка выходило ответом модели «пришлите настоящий
  текст», а заполнение полей падало у ядра с `PAYLOAD_IS_EMPTY`
  (bx-shef/toolsai#11). Теперь первым — готовый `prompt`, шаблон — только
  если готового нет.
* Настройка «Свои промпты для резюме звонка и заполнения полей» (вкладка
  «Провайдер», по умолчанию выключена) — запасной путь, если по готовому
  промпту ядра ответы не годятся. Модуль пишет инструкцию сам по коду
  промпта (`payload_raw`) и маркерам (`payload_markers`): резюме —
  пунктами по фактам; поля — `json_object` с ключами-именами полей CRM и
  `comment` (без него CRM считает ответ пустым — `PAYLOAD_IS_EMPTY`), в CRM
  уходят только известные ей ключи; провайдер без `json_object` — один
  повтор без него, объект в тексте берётся от «{» до «}», как у CRM; не
  объект — `provider_bad_response` с ценой в журнал. Оценка звонка и прочие
  сценарии — всегда промптом ядра.

## 1.0.1 — 2026-09-29

Исправления по ретроспективной панели из пяти проверяющих (документация,
инженер, QA, безопасность, CTO) — правила ревью теперь в
`docs/agent-rules.md`.

Безопасность:

* SSRF через адрес записи: приватные адреса при скачивании — только для
  хоста портала, редиректы проходятся вручную с проверкой каждого шага;
  транспорт больше не ходит по редиректам сам (ни колбэк, ни провайдер);
* задание без `hash` отклоняется (400 `no_hash`): без него не работала
  защита от повторов;
* ротация токена эндпоинта — кнопкой на странице расхода и
  `ROTATE_TOKEN=1 cli/setup.php`; движки не перерегистрировались — токен
  остаётся прежним;
* эндпоинт не создаёт сессию на каждый запрос ядра.

Надёжность:

* любой сбой диспетчера (база, журнал, квота) отдаёт ядру ошибку
  `internal_error`, а не оставляет задание висеть до ttl; сбой записи
  расхода не съедает колбэк с оплаченным результатом;
* колбэк повторяется при недоступности портала (нет соединения, 429, 5xx);
* запись «в работе», брошенная умершим процессом, перехватывается повтором
  задания; сбой вставки в журнал больше не выглядит как «дубликат»;
* скачанная запись с ошибкой транспорта или длиннее 25 МБ не уходит на
  распознавание обрезком;
* агент: сбой эскалации не обрывает прогон и не оставляет сделку без
  отметки; три ошибки провайдера подряд (нет связи, лимит частоты, ключ)
  останавливают прогон, и сделки не помечаются проверенными; сделка, на
  которой падает сама модель, помечается проверенной с ошибкой, а не
  оплачивается каждый прогон; ручной прогон — под той же блокировкой;
* схема ответа анализа сделок — без ключевых слов, которые строгий режим
  structured outputs не принимает;
* откаты по стадиям не считают стадии чужого направления.

Обновление кита (2026-09-29) — новые опоры на ядро:

* движок, выбранный в настройках ИИ: CRM берёт его строго по коду, без
  фолбэка. Выбрать движки модуля — ссылка «Выбрать движок модуля» на
  странице настроек модуля (решение владельца: настройки ИИ портала модуль
  меняет только оттуда); заменяет и прежний выбор, но только
  зарегистрированными движками и audio — только вместе с text. Установщик
  туда не пишет, «Проверить и включить» выбор только показывает
  (`selected *` в отчёте). При удалении модуля наш код снимается с настройки: выбирал
  модуль — возвращается прежний движок, иначе — пусто;
* `audio` без `text` невидим CRM (`ThirdParty::hasQuality()`): отчёт не
  считает audio готовым, если text не зарегистрировался;
* `cli/core-api-guard.php` — версия кита: видимость движка с тем же фильтром
  качества, что в CRM, и выбранный движок;
* документация: гейты 10–13 (выбор по коду, audio требует text, права
  ответственного на дело звонка, одно задание распознавания на дело).

Решения владельца (2026-10-02):

* установка и включение раздельны: установщик только создаёт таблицы,
  заглушки и токен (`Setup::prepare()`); обход BaaS, движки и агент — по
  кнопке «Проверить и включить» (`Setup::run()`). Пометку «обход BaaS
  включил модуль» теперь ставит сам `Setup`, а не установщик: раньше при
  включении кнопкой удаление его бы не сняло. Порталы 1.0.0, где обход
  включали кнопкой, пометки задним числом не получают — удаление оставит
  обход включённым, снять руками: `BaasManager::setIgnored(false)`;
* удаление с `savedata = Y` снимает и пометку `SYS_baasset`: иначе после
  переустановки модуль снял бы обход, включённый уже не им.

Приёмка на коробке 2026-10-02 (bx-shef/toolsai#3, main 26.750, ai 26.1100,
crm 26.800):

* дело старшему при анализе сделки не ставилось: в crm 26.800 конструктор
  `Activity\Entity\ToDo` требует провайдер вторым аргументом —
  `ArgumentCountError`. Провайдер передаётся, если конструктор его ждёт;
* ядро ai ходит на адрес движка только по публичному IP
  (`setPrivateIp(false)` при регистрации и на каждое задание) —
  `01-engine-contract.md` утверждал обратное. Исправлено; «Проверить и
  включить» при отказе регистрации называет причину, если адрес
  резолвится в приватный IP; стенд в Docker — в подсети `198.18.0.0/24`;
* внешний адрес без схемы отчёт называл «не задан» — теперь «не разобран:
  нужен вид https://…»;
* «Выбрать движок модуля» открывалась в новой вкладке (BB `[URL]`), и
  исходная страница оставалась с «не выбран» — теперь обычная ссылка;
* гейт 8 (`AI_BOX_AGREEMENT`) на ai 26.1100 — всегда принят.
* анализ сделок без «старшего» — отчёт прогона пишет «старший не задан —
  дела нет», а не молчит;
* на месте заглушки эндпоинта чужой файл — движки не регистрируются: его
  ответ 200 прошёл бы проверку ядра, и задания ушли бы не туда;
* `docker/stand/test-call.sh` — уникальное имя записи.

Боевая проверка (bx-shef/toolsai#12):

* DeepSeek и другие провайдеры без `response_format: json_schema`:
  `completeJson()` после отказа 4xx повторяет запрос с `json_object` (схема —
  в системном сообщении) и сверяет ответ со схемой сам — анализ сделок на
  них работает; 401/403/429/5xx — без повтора; оплаченный, но негодный
  ответ (не JSON, не по схеме) пишется в журнал с ценой и идёт в квоту;
* настройка «Дополнительные параметры модели текста» (JSON в
  `/chat/completions` как есть) — например, выключить рассуждения DeepSeek,
  которые оплачиваются как выходные токены; модель, сообщения и формат
  ответа не перекрываются; `cli/preflight.php` показывает, применяются ли;
* выбор движков по категориям: «оба / только текст / только
  распознавание» — сценарий «текст модуля, распознавание штатное
  `BitrixAudio`» больше не требует правки настроек ИИ руками;
* адрес настроек ИИ в подсказках и документации — коробочный
  `/configs/?page=ai` (`/settings/configs/` — облачный, на коробке не
  открывается);
* отчёт о выборе движка (`selected …` в «Проверить и включить»,
  `cli/setup.php`, `cli/preflight.php`) называет движок модуля по имени и
  коду вместо «наш»; штатный движок в соседней категории — OK без совета
  заменить его; строки INFO — что выбрано в других сценариях CRM (оценка
  звонка по скрипту, повторные продажи, автоматические дела и антиспам),
  которые модуль не обслуживает;
* `cli/preflight.php` показывает строку из `/etc/hosts` для хоста внешнего
  адреса (BitrixVM пишет домен на локальный IP и может вернуть строку при
  перенастройке).
