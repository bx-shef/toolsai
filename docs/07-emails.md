# Письма в CRM

> Последняя сверка: 2026-10-03 (crm 26.800, mail — дерево боевого портала)

## Что и зачем

Клиенты пишут не только в чат и звонят — они присылают письма. Письма
попадают в CRM делами, но **штатного ИИ для писем в CRM нет**: ни резюме, ни
дел, ни оценки. С 1.7.0 это делает модуль — раз в час, по письмам,
привязанным к сделке или лиду. Четыре функции, каждая включается своим
флажком на вкладке «Письма» (по умолчанию всё выключено):

1. **Резюме входящего письма** — комментарий в ленте сделки: что пишет
   клиент, чего хочет, какие сроки.
2. **Дела менеджеру по входящему письму** — до трёх конкретных дел со
   сроком («Выслать КП на 20 стульев»). Спам, рассылки, автоответы («я в
   отпуске»), уведомления — без дел и без комментария.
3. **Оценка исходящего письма менеджера** — по своим критериям (ответил ли
   на вопрос клиента, вежливость и грамотность, конкретика, следующий шаг):
   процент и невыполненные пункты — комментарием в ленту.
4. **Контроль скорости ответа** — без ИИ: клиент написал, а ему не ответили
   дольше 4 часов — дело менеджеру «Ответить клиенту на письмо от …»; дольше
   суток — дело старшему.

Цифры — на странице «ИИ: статистика» ([05-stats.md](05-stats.md)). Как
включить — [04-runbook.md](04-runbook.md), шаг 7в.

## Как CRM хранит письмо

Сверено по `crm/lib/activity/provider/email.php`,
`crm/classes/general/crm_email.php:1458-1497`,
`crm/lib/activity/mailbody.php`.

| Что | Где |
|---|---|
| письмо | дело `b_crm_act`: `TYPE_ID = 4` (`\CCrmActivityType::Email`), `PROVIDER_ID = CRM_EMAIL` |
| входящее / исходящее | `DIRECTION` 1 / 2 |
| тема, ответственный | `SUBJECT`, `RESPONSIBLE_ID` |
| дата письма / когда появилось в CRM | `START_TIME` / `CREATED` |
| отправитель | `SETTINGS.EMAIL_META.from` |
| сделка, лид, контакт | `b_crm_act_bind` |
| тело | `DESCRIPTION`, тип — `DESCRIPTION_TYPE` (3 — HTML, у писем из почты всегда; 1 — текст, 2 — BB-код) |

**Тело сжато.** Новые письма CRM хранит с `PROVIDER_TYPE_ID =
EMAIL_COMPRESSED` (`CCrmActivity::Add()` зовёт
`Email::compressActivityDescription()`): в `DESCRIPTION` — только начало
текста, до 200 символов, без разметки. Целиком тело — в
`b_crm_act_mail_body` (`Activity\MailBodyTable`, поле `BODY` сжато, ORM
разжимает) по привязке `b_crm_act_mail_body_bind` (`OWNER_TYPE_ID = 6`
— дело, `OWNER_ID` — ID дела); пока идёт перенос старых писем
(`crm::compress_mail_act_stepper_in_progress = Y`) — по ID в
`ASSOCIATED_ENTITY_ID`.

Модуль читает тело сам (`Email\EmailSource::getBody()`), а не штатным
`Email::uncompressActivityDescription()`: если тела в таблице нет, штатный
метод перекачивает письмо с почтового сервера (`Helper\Message::reSyncBody()`)
и пишет в дело. Агенту это ни к чему — нет тела, берём начало текста из
`DESCRIPTION`.

При подключении ящика CRM заводит старые письма с `CREATED` «сейчас». Поэтому
окно «за последние N дней» проверяется и по `CREATED`, и по `START_TIME`.

## Текст письма для модели

`Email\EmailText::prepare()` — чистая логика, тест `tests/email_test.php`.

1. **Разметка.** `head`, `style`, `script`, комментарии — прочь; `br`
   (и `</br>` — так пишет шапку цитаты сам Битрикс), абзацы, блоки, строки
   таблиц — перевод строки, ячейки — пробел; сущности раскрыты, неразрывный
   пробел — пробел; пустые строки схлопнуты.
2. **Цитата прошлой переписки** — режется по признакам:

   | признак | откуда |
   |---|---|
   | всё внутри `<blockquote>` (и вложенные; незакрытый — до конца) | Битрикс (`Mail\Message::wrapTheMessageWithAQuote()`), Apple Mail, многие клиенты |
   | всё после блока с классом или id `gmail_quote`, `yahoo_quoted`, `moz-cite-prefix`, `divRplyFwdMsg`, `appendonsend` и т. п., после `<hr id="stopSpelling">` | Gmail, Yahoo, Thunderbird, Outlook |
   | строки, начинающиеся с `>` | текстовые письма |
   | всё после строки «-----Original Message-----», «-----Исходное сообщение-----», «Forwarded message» | Outlook, пересылка |
   | всё после «On … wrote:», «… пишет:», «… написал(а):» — если в строке есть дата или адрес | Gmail, Mail.ru, iOS |
   | всё после «03.10.2026, 12:00, "Иван" <ivan@x.by>:» | Яндекс |
   | всё после шапки «От кого:/От:/From:», если в следующих строках «Кому:/Отправлено:/Sent:/Date:/Тема:» | Битрикс, Outlook |

   Заголовок цитаты в **первой** строке не режет: письмо, которое целиком
   цитата (переслали), лучше отдать как есть, чем пустым.
3. **Подпись** — после строки «-- », «Отправлено с iPhone», «Sent from my …»;
   после «С уважением», «Best regards» — только если до неё уже есть текст.
4. **Длина** — до 6000 символов (предыдущее письмо клиента в оценке — до
   3000), дальше «…».

Письмо без разметки цитаты и без её заголовка уйдёт модели целиком (в
потолке длины) — это не ошибка, а предел признаков.

**Служебные письма — без модели** (`EmailText::serviceReason()`): адрес
отправителя `mailer-daemon@`, `postmaster@`, `noreply@`, `no-reply@`,
`do-not-reply@`, `bounce…@`; тема начинается с «Автоответ», «Auto:»,
«Automatic reply», «Out of Office», «В отпуске», «Нет на месте»,
«Undelivered», «Delivery Status Notification», «Не доставлено», «Read:». Такое
письмо помечается «не клиент» и в контроль скорости ответа не идёт.

## Входящее письмо: резюме и дела

Один запрос к модели на письмо (`Email\EmailPrompt::incomingMessages()`,
`Email\EmailAnalyzer::analyzeIncoming()`). В справке — менеджер, дата
письма, «сейчас» (от него модель считает «до пятницы») и тема — строкой
JSON; само письмо — сообщением пользователя. Ответ — плоский JSON:

```json
{"is_client": true, "is_actionable": true, "kind": "client",
 "summary": "Клиент просит КП на 20 стульев с доставкой в Минск.",
 "wants": "КП и срок поставки.", "terms": "КП до пятницы.",
 "todos": [{"title": "Выслать КП на 20 стульев", "description": "…", "deadline": "2026-10-09T12:00:00"}]}
```

Разбор — `EmailPrompt::normalizeIncoming()`:

* `is_client` — строго `true`/`false` (строки «true»/«false» тоже); нет или
  мусор — ответ негодный: `provider_bad_response` с расходом, письмо
  помечается ошибкой (за него уже заплачено);
* не клиент (`kind`: spam, newsletter, autoreply, notification, internal,
  other) — без дел, без комментария, в контроль скорости ответа не идёт;
* `is_actionable = false` («спасибо, получили») — без дел;
* дел не больше трёх, без названия — из описания; срок — годный
  `ГГГГ-ММ-ДДTчч:мм:сс` в будущем, иначе через 24 часа.

Что пишется в CRM:

* флажок «Резюме» — комментарий в ленту сделки (лида):

  ```
  ИИ: письмо клиента от 03.10.2026 12:30 «Re: КП».
  Что пишет: …
  Чего хочет: …
  Сроки: …
  Дела менеджеру: «Выслать КП на 20 стульев».
  ```

* флажок «Дела» — дела «Сделать» (To-Do) в сделке (лиде); ответственный —
  ответственный письма (`RESPONSIBLE_ID`), нет — сделки.

Включён только один флажок — запрос всё равно один, пишется только своё.

## Исходящее письмо: оценка

Один запрос на письмо (`EmailPrompt::reviewMessages()`,
`EmailAnalyzer::review()`). Модели — письмо менеджера и **предыдущее
входящее письмо клиента в той же сделке** (последнее до исходящего; нет —
так и сказано, и критерий «ответил на вопрос» получает `null`). Ответ — та же
форма, что у оценки звонка и чата (`criteria`, `overall_summary`,
`recommendations`), разбор — `CopilotPrompt::normalizeScoring()`.

Критерии — настройка «Критерии оценки исходящего письма», критерий на
строку (до 20; нумерация и маркеры списка снимаются). Пусто — встроенные
(`EmailPrompt::DEFAULT_CRITERIA`):

1. Ответил на вопрос клиента из его предыдущего письма.
2. Вежливо: приветствие, обращение к клиенту, подпись.
3. Грамотно и понятно: без ошибок и опечаток.
4. Конкретно: цены, сроки, наличие — если о них речь.
5. Назван следующий шаг или призыв к действию.

Процент — как у звонка в CRM: выполненные от оценённых, `null` не в счёт
(`ChatScore::percent()`). Комментарий в ленту:

```
ИИ-оценка письма менеджера «КП»: 75%.
Не выполнено: Конкретно: цены, сроки, наличие — если о них речь.
Итог: …
Что сделать иначе: …
```

Письма короче 30 символов после очистки («Спасибо, получили») не
оцениваются — без модели.

## Контроль скорости ответа

Без модели, `Email\ReplyClock` (чистая логика) и
`Agent\EmailAgent::watch()`.

* **Ответ** на входящее письмо — исходящее письмо или **исходящий** звонок,
  привязанные к той же сделке (лиду), созданные не раньше входящего.
  Входящий звонок клиента — не ответ.
* **Время** — от `CREATED` входящего письма (когда оно появилось в CRM:
  раньше менеджер его не видел) до `CREATED` ответа.
* **Часы — простые, календарные.** Рабочего графика модуль не знает (так
  решил владелец): ночь и выходные считаются. Письмо пятницы 18:00 к
  понедельнику 9:00 ждёт 63 часа — и получит и дело менеджеру, и дело
  старшему. Не устраивает — поднять пороги.
* **Пороги** — `EMAIL_replyhours` (4 ч) — дело менеджеру «Ответить клиенту на
  письмо от …» сроком 2 часа; `EMAIL_escalatehours` (24 ч) — дело старшему
  «Клиент без ответа N ч» сроком сутки.
* **Неотвеченные письма одной сделки — одна группа**: время — от самого
  старого, дело менеджеру и дело старшему — по одному на группу.
  Отметка ложится на все ждущие письма сделки (`REPLY_TODO_AT`,
  `SENIOR_TODO_AT`), и новое письмо клиента до ответа дело не повторит.
  Ответили — письма группы получают `REPLIED_AT` и `REPLY_SECONDS` (сколько
  ждал клиент) и из контроля уходят.
* **Старший** — из профиля анализа сделок, который подходит сделке
  (направление и тип клиента, `Deal\ProfilePicker`), если у профиля задан
  старший; иначе — настройка `EMAIL_senior`; у лидов — сразу она. Нет
  нигде — дела старшему нет, отчёт прогона говорит «старший не задан».
* **Окно** — письма за `EMAIL_days` дней, но не меньше `EMAIL_escalatehours`
  + сутки, до 500 писем за прогон (SQL без модели).
* Письма, которые модель или проверка без модели признали не клиентскими, в
  контроль не идут. Входящее, которое моделью ещё не разбиралось (резюме
  выключено), под контролем — проверяется только адрес и тема.

Проверяется раз в прогон агента: при интервале 60 минут дело приходит в
течение часа после порога.

## Анализ сделки

В сводку для модели анализа сделок ([02-deal-health.md](02-deal-health.md))
добавлены (`Deal\ContextBuilder`, `Deal\DealFacts`):

* «Клиент ждёт ответа на письмо: N ч» — самое старое входящее письмо после
  последнего ответа (`ReplyClock::waitingSince()`); письма, признанные не
  клиентскими, не в счёт;
* резюме двух последних входящих писем, которые разобрал модуль.

Сделка, где есть только письма, теперь «есть о чём рассуждать»
(`DealFacts::isWorthAnalyzing()`).

## Путь агента

`Agent\EmailAgent` — раз в `DEAL_interval` минут (60), под своей
блокировкой (`Constants::LOCK_GROUP_EMAIL`), от служебного пользователя,
если включена хоть одна функция. Ручной прогон — `cli/emails.php`
(`ACTIVITIES=101,102` — только эти письма, без окна; контроль скорости — не
по списку).

1. Входящие (резюме или дела включены): кандидаты —
   `Email\EmailSource::getCandidates()`, письма за окно, привязанные к
   сделке или лиду, моделью не разобранные; сначала давние. Сделка или
   лид — как у чатов (`Chat\DialogSource::pickOwner()`: сделка важнее).
2. Исходящие (оценка включена): так же.
3. Контроль скорости ответа (включён).

`EMAIL_maxperrun` — запросов к модели за прогон на всё вместе, входящие
первыми. Служебные, пустые и короткие письма модель не зовут и в лимит не
входят. Квота исчерпана или провайдер не ответил три раза подряд — прогон
стоп. Расход — журнал `shef_toolsai_usage`, категория `email`, код
`sheftoolsai_email`: «в работе» с оценкой цены до запроса, итог после.
Провайдер текста — заглушка: ответ без модели и денег — «клиент», резюме с
пометкой `[заглушка]`, без дел; оценка — все пункты выполнены.

## Таблица `shef_toolsai_email`

Строка на дело-письмо (`ACTIVITY_ID` уникален).

| поле | что |
|---|---|
| `ACTIVITY_ID`, `OWNER_TYPE_ID`, `OWNER_ID` | письмо и сделка (2) или лид (1) |
| `DIRECTION`, `RESPONSIBLE_ID`, `MAIL_AT` | направление, ответственный письма, `CREATED` письма |
| `MODE` | тип обработки: `SUMMARY` — входящее разобрано, `REVIEW` — исходящее оценено, `WATCH` — только контроль скорости |
| `STATUS` | `DONE`; `SKIPPED` — без модели (служебное, пустое, короткое, нет сделки); `ERROR` — модель ответила негодно (оплачено); пусто — моделью не обрабатывалось |
| `IS_CLIENT` | `Y` / `N` / пусто — не разбиралось |
| `SUMMARY`, `RESULT` | резюме или итог оценки; ответ модели после нормализации (у оценки — `{"criteria": [...]}`, читает `Stats\ScoreResult`) |
| `SCORE`, `TODO_COUNT` | процент оценки; поставлено дел |
| `REASON`, `ANALYZED_AT` | причина пропуска или сбоя записи в CRM; когда разобрано |
| `REPLIED_AT`, `REPLY_SECONDS` | первый ответ клиенту и сколько он ждал |
| `REPLY_TODO_AT`, `SENIOR_TODO_AT` | поставлено дело менеджеру / старшему — повтора нет |
| `CREATED_AT` | когда появилась строка |

Создаётся и дописывается идемпотентно (`Email\Model\EmailTable::init()`):
установщик, «Проверить и включить», агент. Уходит с модулем без
`savedata = Y`. Сбой провайдера (нет связи, лимит, ключ) строку не пишет —
письмо снова кандидат.

## Настройки (вкладка «Письма»)

| код | что | умолчание |
|---|---|---|
| `EMAIL_summary` | резюме входящего в ленту | `N` |
| `EMAIL_todos` | дела менеджеру по входящему | `N` |
| `EMAIL_review` | оценка исходящего | `N` |
| `EMAIL_reply` | контроль скорости ответа | `N` |
| `EMAIL_maxperrun` | запросов к модели за прогон, 1–200 | 20 |
| `EMAIL_days` | письма за последние N дней, 1–60 | 3 |
| `EMAIL_criteria` | критерии оценки, на строку; пусто — встроенные | — |
| `EMAIL_replyhours` | дело менеджеру после N часов без ответа, 1–168 | 4 |
| `EMAIL_escalatehours` | дело старшему после N часов, 1–720 | 24 |
| `EMAIL_senior` | ID старшего, если нет профиля со старшим | — |

Вне границ или мусор — умолчание. Интервал агента — общий с анализом
сделок (`DEAL_interval`), применяется кнопкой «Проверить и включить».

## Что не проверено

* Всё, что касается базы и ядра, — на заглушках: SQL кандидатов и ответов,
  чтение тела из `b_crm_act_mail_body` (`MailBodyTable`,
  `ActMailBodyBindTable`), `SETTINGS.EMAIL_META.from`,
  `CommentEntry::create()` и `ToDo` в лиде, подбор старшего по профилю.
  **Проверяется на стенде.**
* Признаки цитаты и подписи сверены с разметкой Битрикса (шаблон цитаты
  модуля mail) и с известными форматами почтовиков, но не на живой почте
  портала. Новый формат цитаты — письмо уйдёт модели с цитатой (дороже, но
  не сломается).
* Исходящие письма роботов и рассылок CRM (если они попадают делами
  `CRM_EMAIL`) оцениваются как письма менеджера — отличить их по полям дела
  не нашёл. Короткие отсекаются порогом 30 символов.
* Сделка в финальной стадии не исключается из контроля скорости ответа:
  клиент, написавший в закрытую сделку, тоже ждёт ответа.
