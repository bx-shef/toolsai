# Анализ сделки: «пора звать старшего»

## Почему не штатными средствами

### `AnalyzeCommunication` — это не оценка риска

`crm/lib/integration/ai/dto/analyzecommunicationpayload.php`:

```php
public array $actions = [];              // до 5 дел-напоминаний
public bool $isClient = false;
public ?string $reasonIfIsClientFalse = null;
```

Операция превращает разговор в список задач. Ни балла риска, ни флага
эскалации там нет и не предполагается.

### Узел автоматизации «AI-обработка» недоступен

`ai/install/activities/bitrix/aiprocessingactivity/` — готовый узел роботов.
Параметры (`aiprocessingactivity.php:24-36`): `prompt`, `returnType`
(`text`/`json`), `jsonSchema`, `jsonPath`, `usePseudonymizer`; возвращает
`aiResult` и `errorMessage`. Ровно то, что нужно.

Но `.description.php:36`:

```php
->setExcluded(!Loader::includeModule('ai') || !$isAiNodeAvailable)
```

`$isAiNodeAvailable` -> `NodeAvailabilityService::isAvailable()`
(`bizproc/lib/Public/Service/AiAgent/NodeAvailabilityService.php:13,36`)
требует модуль **`aiassistant`**, которого на коробке нет. Узел не появится
в конструкторе, а при запуске выйдет на `execute()` строка 105-110.

Регион не мешает — заблокирована только `cn`
(`RegionAvailabilityService.php:13`).

**Если `aiassistant` у вас появится** — этот узел становится самым дешёвым
путём: всё собирается мышкой, без кода. Проверить наличие:
`cli/core-api-guard.php`, раздел «ВЕРСИИ».

## Как устроено у нас

```
DealHealthAgent (по расписанию)
    v
ProfileMigration::run()        таблицы и перенос старых настроек (один раз)
    v
getCandidates()                открытые сделки направлений с профилями;
                               в SQL отсеяны финальные стадии (S/F) и
                               мёртвые (ACTIVE_DAYS)
    v
ContextBuilder::build()        факты о сделке -> DealFacts
                               (направление, ответственный, тип клиента,
                               запланированные и просроченные дела,
                               резюме и оценки последних звонков,
                               резюме писем и «ждёт ответа N ч» — 1.7.0)
    v
ProfilePicker::pick()          профиль к сделке; нет — пропуск без ИИ
    v
DealFacts::isAlive()           живая ли сделка (ACTIVE_DAYS профиля)
    v
DealFacts::isWorthAnalyzing()  ДЕШЁВЫЙ ФИЛЬТР без ИИ (IDLE_DAYS профиля)
    v
HealthAnalyzer::analyze()      промпт профиля + JSON Schema -> LLM
    v
Verdict {risk, needSenior, why, nextStep}
    v
RiskScale::decide()            шкала профиля -> ScaleDecision
    v
Escalation::apply()            дело менеджеру (+ старшему о просрочке) /
                               таймлайн + дело старшему
```

### Профили

Профиль — как скрипт речевой аналитики CRM
(`crm/lib/Copilot/CallAssessment`, `CopilotCallAssessmentTable`). Таблица
`shef_toolsai_deal_profile` (`Deal\Model\DealProfileTable`), страница
«ИИ: профили анализа сделок» — `/bitrix/admin/shef_toolsai_deal_profiles.php`
(пункт в меню модуля; только администратор).

| Поле | Смысл |
|---|---|
| `ID`, `TITLE`, `IS_ENABLED` (Y/N), `SORT` | как обычно |
| `CATEGORY_ID` | направление сделки |
| `CLIENT_TYPES` | коды типа клиента через запятую: 1 новый, 2 в работе, 3 повторное обращение, 4 вернувшийся покупатель; пусто — любой |
| `PROMPT` | свой системный промпт целиком; пусто — общий (`HealthAnalyzer::getSystemPrompt()`) |
| `IDLE_DAYS` | сделка «зависла», если дел не было N дней (3) |
| `REANALYZE_DAYS` | повторный анализ и повторные дела не чаще, дней (7) |
| `LOW_BORDER`, `HIGH_BORDER` | границы риска 0-100 (50, 70); верхняя не ниже нижней |
| `SENIOR_ID` | старший профиля; 0 — при высоком риске только комментарий |
| `ACTIVE_DAYS` | только живые сделки: последняя активность не старше N дней (60); 0 — без ограничения. С 1.4.0 |

**Промпт.** JSON-схема ответа (`HealthAnalyzer::SCHEMA`) общая и всегда
уходит от модуля — профиль её не меняет. К своему промпту модуль дописывает
короткое требование ответа JSON (`HealthAnalyzer::JSON_RULE`), чтобы
промпт, написанный без оглядки на схему, не ломал разбор.

**Подбор профиля** — `ProfilePicker::pick()`, чистая функция:

1. только включённые профили с направлением сделки;
2. тип клиента — штатно: `Bitrix\Crm\Client\ClientTypeResolver` по
   компании сделки, нет компании — по контакту (`ClientType::pickClient()`); перевод в коды — как
   `AssessmentClientTypeResolver::resolveByIdentifier()`
   (`Deal\ClientType::fromCoreName()`);
3. профиль с этим типом главнее профиля «любой»; тип не определился —
   подходит только «любой»;
4. дальше — меньший `SORT`, потом меньший `ID`.

Нет профиля — сделка отмечается проверенной («Нет подходящего профиля
анализа») без запроса к модели.

#### Как определяется тип клиента

Тип считает ядро (`crm/lib/Client/ClientTypeResolver.php`), модуль только
говорит, по кому. Клиент сделки — её компания; нет компании — контакт (с 1.2.0; раньше
было наоборот). Сделка с компанией и контактом оценивается по истории
компании. Нет
ни того ни другого — тип «не определён», и сделке подходят только профили,
где не отмечен ни один тип («любой клиент»).

| Тип | Код | Когда |
|---|---|---|
| Вернувшийся покупатель (`WithSale`) | 4 | у клиента есть хотя бы одна сделка в успешной стадии (в том числе сама эта сделка, если она выиграна) |
| Повторное обращение (`PreviouslyContacted`) | 3 | успешных сделок нет, но есть проваленная |
| Новый (`New`) | 1 | клиент создан меньше часа назад; в классическом режиме CRM (с лидами) контакт и компания новыми не бывают никогда — ядро сразу считает их «в работе» |
| В работе (`Existing`) | 2 | всё остальное |

Сделку анализируют через дни после создания, поэтому «новый» здесь почти не
встречается — в форме профиля он так и подписан. Профиль без отмеченных
типов подходит любому клиенту, включая сделки, где тип не определился.

**Шкала** — `RiskScale::decide()`, чистая функция:

| Риск | Что делаем |
|---|---|
| ниже `LOW_BORDER` | ничего, только запись о проверке |
| от `LOW_BORDER` | дело ответственному (`ASSIGNED_BY_ID`), **только если у сделки нет запланированных дел** (`COMPLETED = 'N'`) |
| от `HIGH_BORDER` и `needSenior` | ещё комментарий в таймлайне и дело старшему профиля |

`needSenior` от модели для старшего по-прежнему обязателен
(`Verdict::shouldEscalate()`): модель отличает «можно спасти
вмешательством» от «уже мертва». Высокий риск без `needSenior` — уровень
менеджера: дело ему, если дел нет. Ответственный и есть старший — одно дело
(старшему), а не два одному человеку.

Дело менеджеру — To-Do с дедлайном 24 ч, тем же механизмом, что дело
старшему:

```
ИИ-анализ сделки: нет запланированных дел, риск N%.
Что сделать: …
Почему: …
```

Повторы — не чаще `REANALYZE_DAYS` профиля: дело менеджеру — по
`MANAGER_TODO_AT`, эскалация — по `ESCALATED_AT` в таблице проверок
(`shef_toolsai_deal_check`; там же `PROFILE_ID` — каким профилем
проверяли).

### Переход с 1.0.x

Механизма updater у модуля нет: обновление — новые файлы без вызова
установщика. Поэтому `Deal\ProfileMigration::run()` идемпотентный и
зовётся там, где модуль и так бывает: кнопка «Проверить и включить»
(`Setup::run()`), агент и `cli/deal-health.php` перед прогоном, страница
профилей при открытии. Он:

1. создаёт таблицу профилей и дописывает в таблицу проверок столбцы
   `MANAGER_TODO_AT`, `PROFILE_ID`;
2. если профилей ещё нет — переносит старые настройки: по профилю на каждое
   направление из `DEAL_categories`, `LOW_BORDER = HIGH_BORDER =
   DEAL_threshold`, старший — `DEAL_senior`, сроки — `DEAL_reanalyzedays`,
   `DEAL_idledays`, промпт пустой (общий), тип клиента — любой;
3. ставит отметку `SYS_profilesmigrated = Y` — больше не переносит.

Старые настройки не стираются (откат на 1.0.x работает), но на странице
настроек их больше нет. Направления не были выбраны — профилей не будет,
агент ничего не анализирует, пока профиль не заведут руками.

Заметное отличие после переноса: при `LOW = HIGH = порог` у сделки с
риском от порога и без запланированных дел теперь появляется ещё и дело
ответственному (раньше — только старшему).

### Живые сделки, финальные стадии, просрочка (1.4.0)

Боевой прогон 1.3.0: из 100+ кандидатов агент брал 20, почти все — сделки
2024-2025 годов без активности 575-780 дней. Модель честно отвечала «риск
100%, старший не нужен — мертва», у сделок висели старые незакрытые дела,
и никому ничего не ставилось. Плюс сделка в стадии `C14:WON` с
`CLOSED = 'N'` попала в анализ.

**Финальные стадии.** В выборке кандидатов, кроме `CLOSED = 'N'`, —
`STAGE_SEMANTIC_ID` не `S` и не `F` (`Bitrix\Crm\PhaseSemantics`); пустая
семантика (NULL) проходит.

**Живые сделки — `ACTIVE_DAYS` профиля.** «Активность» — время создания
дела, привязанного к сделке (`b_crm_act.CREATED` через `b_crm_act_bind`):
звонки, письма, встречи, дела. Дела, созданные служебным пользователем
агента (`AUTHOR_ID`), не считаются — иначе дело, которое агент поставил
менеджеру, «оживляло» бы мёртвую сделку на 60 дней. Сделка, созданная
позже границы, — живая.

Почему не `DATE_MODIFY` сделки: её сдвигает любая правка — массовая смена
ответственного, робот, импорт, — и мёртвые сделки «оживали» бы пачками. И
не `LAST_ACTIVITY_TIME` ядра: его двигают в том числе комментарии в
таймлайне (`Timeline\Monitor`), а агент сам пишет комментарий от имени
старшего. Минус выбора: смена стадии без дела активностью не считается —
обычно рядом есть звонок или дело.

Фильтр в двух местах: в SQL выборки кандидатов (`getCandidates()`, по
самому мягкому `ACTIVE_DAYS` среди профилей направления,
`ProfilePicker::getCategoryActiveDays()`) — чтобы мёртвые не занимали лимит
прогона; и точно по профилю сделки — `DealFacts::isAlive()` до модели.
Пропуск пишется как проверка («Нет активности N дн.»).

**Запланированные и просроченные дела.** Состояние дела —
`DealFacts::activityState()` по полям `b_crm_act`:

| `COMPLETED` | `DEADLINE` | состояние |
|---|---|---|
| `Y` | любой | завершено |
| `N` | NULL или 9999 год («без срока») | запланировано |
| `N` | сейчас или позже | запланировано |
| `N` | в прошлом | просрочено |

«Без срока» ядро хранит максимальной датой базы — 9999 год
(`CCrmDateTimeHelper::GetMaxDatabaseDate()` / `IsMaxDatabaseDate()`); она
всегда в будущем. В сводку для модели — обе строки: запланированных и
просроченных (с датой самого старого).

Шкала: дело менеджеру — если риск ≥ `LOW_BORDER` и **нет запланированных**
дел; просроченные от дела не освобождают. Если при этом есть просроченные,
старшему профиля — дело «У менеджера <имя> просрочены дела по сделке: N
шт., самое старое с <дата>. Проконтролировать.» с риском и «почему». Не
ставится, если старшего нет, он же ответственный или ему и так уходит дело
эскалации. Повтор — не чаще `REANALYZE_DAYS` (`OVERDUE_NOTIFIED_AT` в
таблице проверок). Цифра — на странице «ИИ: статистика».

**Содержание звонков.** Для последних 3 звонков сделки в сводку идёт то,
что уже насчитал Копилот (`b_crm_ai_queue`, `ENTITY_TYPE_ID = 6`, только
`SUCCESS`; разбор — `Deal\CallInsights`): резюме (`TYPE_ID = 2`,
`{"summary"}`, до 400 символов), оценка по скрипту (`TYPE_ID = 4` — балл из
`b_crm_ai_quality_assessment.ASSESSMENT`, до 5 невыполненных пунктов, где
`status = false`), признак «не клиент» с причиной (`TYPE_ID = 9`,
`isClient = false`). Общий промпт велит на них опираться.

**Письма (1.7.0).** Если модуль разбирает письма ([07-emails.md](07-emails.md)),
в сводку идут резюме двух последних входящих писем клиента
(`shef_toolsai_email`) и строка «Клиент ждёт ответа на письмо: N ч» — от
самого старого входящего письма после последнего исходящего письма или
звонка (`Email\ReplyClock::waitingSince()`); письма, признанные не
клиентскими, не в счёт. Ждёт ли клиент ответа, считается и без разбора
писем — по делам сделки.

### Время прогона и интервал агента

Агент — раз в `DEAL_interval` минут (60). Новый интервал применяет
«Проверить и включить» (`Setup::ensureAgent()`): агент есть с другим
интервалом — `CAgent::Update()`, а если следующий запуск назначен дальше
нового интервала (был раз в сутки), он переносится ближе
(`Setup::planAgentUpdate()`, тест `setup_test.php`).

Прогон — до `DEAL_maxperrun` (50) анализов по 2-4 с: до 3-4 минут, при
сбоях провайдера — до трёх таймаутов. **Агенты портала лучше держать на
cron** (`BX_CRONTAB_SUPPORT`): на хитах прогон держит чей-то запрос
страницы минутами. Агент снимает лимит времени (`set_time_limit(0)`,
`ignore_user_abort`) — иначе `max_execution_time` обрывал бы прогон между
оплаченным ответом и записью о проверке. Блокировка `runLocked()` не
меняется: второй прогон, пока идёт первый, просто выходит.

### Почему сводка, а не транскрипт

В промпт уходит `DealFacts::toPromptText()` — компактная выжимка: дни без
активности, откаты по стадиям, доля неотвеченных звонков, резюме последних
разговоров. Не сырые транскрипты.

Две причины:

1. **Дешевле.** Пять транскриптов по 20 минут — это десятки тысяч токенов на
   одну сделку. Сводка укладывается в сотни.
2. **Точнее.** Риск потери сделки виден в динамике, а не в одном разговоре.
   Модель, которой дали пять стенограмм, начинает пересказывать последнюю.

### Почему фильтр до модели

`DealFacts::isWorthAnalyzing()` отсекает свежие и живые сделки без единого
запроса. При сотне открытых сделок и ежедневном прогоне это разница между
~3000 и ~300 запросами в месяц.

Порог «в работе» — поле профиля `IDLE_DAYS`.

### Почему JSON Schema, а не свободный текст

`HealthAnalyzer::SCHEMA` задаёт строгую форму ответа. Свободный текст пришлось
бы парсить регулярками, и любая смена настроения модели ломала бы разбор.
Со схемой ответ либо валиден, либо провайдер честно падает.

## Что настроить

Страница настроек модуля, вкладка «Анализ сделок»:

| Опция | Смысл |
|---|---|
| `DEAL_enabled` | включить агент (по умолчанию выключен); сам агент регистрирует «Проверить и включить» — без неё флажок ничего не делает |
| `DEAL_maxperrun` | анализов за прогон, не больше (50) |
| `DEAL_interval` | запускать агент раз в N минут (60, от 10 до 10080); применяется кнопкой «Проверить и включить» |

Всё остальное — направления, типы клиента, промпты, границы риска,
старшие, сроки — в профилях (см. выше). Без включённого профиля агент не
работает.

Прогон руками, с отчётом: `php -f cli/deal-health.php`, по конкретным
сделкам — `DEALS=15,16 php -f cli/deal-health.php`.

## Про расход

Один анализ сделки = 1 запрос к LLM. Агент — главный потребитель квоты, и
единственный компонент, который может незаметно съесть месячный бюджет за
неделю.

**Куда уходит запрос** (с 1.5.0). Включается анализ провайдером «Текст» на
вкладке «Движок», а адрес, ключ, модель, цены и таймаут — свои, вкладка
«Провайдер», блок «Анализ сделок» (`API_dealbaseurl`, `API_dealapikey`,
`API_dealmodel`, `API_dealpricein`/`API_dealpriceout`, `API_dealtimeout`).
Пусто — как у текста Копилота, у текста пусто — общие. Так анализ можно
отдать модели подешевле (или помощнее), чем резюме звонков. Подробно —
[04-runbook.md](04-runbook.md), шаг 6.

Поэтому в `DealHealthAgent` ограничители: `DEAL_maxperrun`,
`REANALYZE_DAYS` профиля, `ACTIVE_DAYS` профиля (мёртвые не анализируются),
фильтр `isWorthAnalyzing()` (`IDLE_DAYS` профиля) и сам подбор — сделку без профиля модель не видит.

**Начинай с одного профиля и небольшого лимита.** Неделю посмотри
страницу «ИИ: расход и остаток» (строка `deal/SUCCESS`), потом расширяй.
