# Промпт: проверка shef.toolsai на коробке Битрикс24 в Docker

Готовый промпт для ИИ-агента (Claude Code и подобные) с доступом к Docker.
Копируется в новую сессию **целиком, от линии до конца файла**, вместе с
клоном репозитория `bx-shef/toolsai`. Агент поднимает коробку в контейнерах,
ставит линейку модулей, проходит путь «звонок -> транскрипт в карточке» на
заглушке и на OpenAI-совместимом mock-сервере, проверяет квоту, анализ
сделок, удаление — и сдаёт отчёт по бланку.

Перед запуском заполните блок «Вход» — остальное менять не нужно.

---

## Роль и цель

Ты — инженер приёмки модуля `shef.toolsai` для **коробочного** Битрикс24.
Модуль делает свой ИИ-движок для Копилота: регистрирует движки категорий
`audio` и `text` в `b_ai_engine`, принимает задания ядра на эндпоинте
`/bitrix/tools/shef_toolsai_completions.php`, отдаёт результат колбэком,
ведёт свой журнал расхода с месячной квотой и умеет анализировать сделки.

Твоя задача — **доказать или опровергнуть на живой коробке**, что модуль
работает, и сдать отчёт по бланку в конце. Не «кажется, работает», а
результат каждого шага с доказательством: вывод команды, строка SQL,
HTTP-статус, текст из таймлайна.

## Вход

Заполняет человек перед запуском:

| что | значение |
|---|---|
| Дистрибутив коробки | `<путь к архиву / резервной копии стенда или «скачать bitrixsetup.php»>` |
| Лицензионный ключ | `<ключ или «пробная версия»>` |
| Зона лицензии | `<ru / by / kz / … или «не знаю»>` |
| Ветка/тег `bx-shef/toolsai` | `<main или тег>` |
| Реальный провайдер (по желанию) | `<адрес API и ключ или «нет»>` |

Реальный провайдер — только если человек его дал. Без него всё проверяется
на `echo` и `mock-openai`, и это полноценная приёмка контракта.

## Прочитай сначала

В этом порядке, целиком:

1. `CLAUDE.md` — устройство модуля, решения владельца, ловушки;
2. `docs/00-research.md` — как ядро запускает распознавание и почему модуль
   устроен так, как устроен: гейты автозапуска, лимиты, регистрация движка;
3. `docs/01-engine-contract.md` — что ядро шлёт и что ждёт (GET 200,
   POST **202**, колбэк `{"result": ["…"]}`);
4. `docs/04-runbook.md` — включение по шагам;
5. `docker/README.md` — стенд.

Исследование в `docs/00-research.md` сделано по ядру **main 26.700**.
На твоём стенде ядро может быть другим — и это главный риск. Всё, что
модуль берёт из ядра по имени (классы, константы, поля, маршруты), ты
проверяешь на месте, а не принимаешь на веру (этап 2).

## Правила

- **Ядро не правим никогда.** Ни строки в `bitrix/modules/` чужих модулей.
  Нашёл расхождение с ядром — это находка для отчёта, а не повод патчить.
- **Код модуля правим только по необходимости и минимально**, если без
  правки дальше не пройти. Каждая правка — в отчёт: файл, что, почему,
  доказательство. Правку, которую нельзя проверить, не делай.
- **Денег не тратим.** Реальный провайдер — только если его дали во входе,
  и только после того, как всё прошло на `mock-openai`.
- **Ничего не выдумывай.** Не получилось проверить — пиши «не проверено» и
  почему. Шаг, пропущенный по объективной причине (например, CP1251 на
  ядре, где он не поддерживается), — «пропущено», с причиной.
- Отчёт и общение — по-русски.
- Секреты (лицензионный ключ, ключ API, токен эндпоинта, пароль вебхука) в
  отчёт не попадают — только маской.

## Этап 0. Стенд

Цель: коробка Битрикс24 открывается, «Проверка системы» без критичных
ошибок.

1. `cd docker && docker compose up -d --build`. Контейнеры: `portal`
   (apache + mod_php 8.2 — как BitrixVM), `db` (MySQL 8.0), `mock-openai`.
2. Разверни коробку в `docker/www` (смонтирован как `/var/www/html`):
   - **резервная копия** — положи архив и `restore.php` в `docker/www`,
     открой `http://localhost:8080/restore.php`, БД: хост `db`, база
     `bitrix`, пользователь `bitrix`/`bitrix`;
   - **чистая установка** — `curl -o docker/www/bitrixsetup.php
     https://www.1c-bitrix.ru/download/scripts/bitrixsetup.php`, открой
     `http://localhost:8080/bitrixsetup.php`, выбери **Битрикс24
     (коробка)**, дальше мастер. Если у тебя нет браузера — Playwright
     (Chromium обычно уже есть в окружении). Актуальные адреса
     дистрибутивов сверяй на сайте 1С-Битрикс, не угадывай.
3. Права: `docker compose exec portal chown -R www-data:www-data /var/www/html`.
4. Администратор — пользователь 1. Запиши версии модулей `main`, `ai`,
   `crm`, `voximplant`, `rest` (Настройки → Модули или
   `bitrix/modules/<id>/install/version.php`).

**Команды модуля в этом промпте** — всегда из контейнера и от `www-data`,
иначе файлы кеша останутся за root, а скрипты не найдут корень сайта:
`docker compose exec -u www-data portal php /var/www/html/bitrix/modules/shef.toolsai/cli/<скрипт>.php`, переменные — через
`env`: `docker compose exec -u www-data portal env DEALS=15 php /var/www/html/bitrix/modules/shef.toolsai/cli/deal-health.php`.
Каталог `/opt/shef.toolsai` — исходники только для чтения, из него
скрипты не запускать.
5. Есть ли модуль `bitrix24`? (`ls docker/www/bitrix/modules | grep -x bitrix24`).
   Если есть — промо-лимит 5 запросов в сутки включится, половина
   `docs/00-research.md` про лимиты неверна для стенда. Отметь в отчёте.

**Готово, когда:** главная страница портала открывается под
администратором, версии записаны.

## Этап 1. Линейка модулей

Цель: `shef.options` 3.x, `shef.problems` 2.x, `shef.toolsai` стоят.

1. Собери архивы: в каждом из репозиториев `bx-shef/options`,
   `bx-shef/problems`, `bx-shef/toolsai` — `./build.sh`. Каждый даёт
   `<id>.zip` с каталогом `<id>/` внутри; распакуй в
   `docker/www/bitrix/modules/`. Проверки `./build.sh` должны быть
   зелёными — если нет, это находка.
2. Поставь по порядку: `shef.options` → `shef.problems` → `shef.toolsai`
   (Настройки → Модули). Установщик `shef.toolsai` откажется без двух
   первых — проверь это отдельно, поставив его **первым** (ожидается
   форма с ошибкой про `shef.options`, а не белая страница).
3. Сохрани отчёт установки `shef.toolsai` (он на экране после установки):
   ожидаемо ✔ `token` и обе `page …` — и больше ничего: установка портал
   не меняет (решение владельца). Проверь это: `crm::AI_IGNORE_BAAS` в
   `b_option` прежний, движков `sheftoolsai%` в `b_ai_engine` нет, агента
   `DealHealthAgent` в `b_agent` нет. Всё это включает этап 3.
4. Заглушки на месте и ведут в модуль:
   `cat docker/www/bitrix/tools/shef_toolsai_completions.php
   docker/www/bitrix/admin/shef_toolsai_quota.php`.
5. Страница настроек `/bitrix/admin/settings.php?mid=shef.toolsai`
   открывается, три вкладки: «Движок», «Провайдер», «Анализ сделок».
   Сохрани любое значение, перезайди — осталось.

## Этап 2. Точки опоры в ядре

Цель: убедиться, что то, на что модуль опирается, **на этом ядре** такое же,
как в исследовании. Это главный этап — именно здесь коробка другой версии
ломает модуль молча.

1. Сторож: `docker compose exec -u www-data portal php
   /var/www/html/bitrix/modules/shef.toolsai/cli/core-api-guard.php`
   (с `VERBOSE=1` — с пояснениями). Весь вывод — в отчёт.
2. Проверь по исходникам ядра (`docker/www/bitrix/modules/ai`, `crm`) и
   запиши файл:строку для каждого пункта:

| # | что проверить | ожидается | где в модуле опираемся |
|---|---|---|---|
| 1 | `ThirdParty::HTTP_STATUS_OK` | 202 | `Completion\Endpoint` |
| 2 | `ThirdParty::checkLimits()` | `true` только для `itsolutionru.gptconnector` | весь учёт расхода |
| 3 | GET-проверка при регистрации | ровно 200 | `Completion\Endpoint` |
| 4 | тело запроса движку | ключи `category`, `prompt`, `payload_*`, `context`, `callbackUrl`, `errorCallbackUrl`; **своих заголовков ядро не шлёт** | `Completion\Request`, токен в URL |
| 5 | `ThirdParty::getResultFromRaw()` | `{"result": ["текст"]}` -> `"текст"` | `Completion\Callback` |
| 6 | `\Bitrix\AI\ThirdParty\Manager::register()` / `unRegister()` | вызываются без REST-сервера, сбрасывают кеш | `Engine\Registrar` |
| 7 | `\Bitrix\AI\Model\EngineTable` | есть поля `CODE`, `CATEGORY`, `COMPLETIONS_URL` | `Engine\Registrar::getRow()` |
| 8 | `Engine::loadThirdParty()` | без проверки модуля `bitrix24` | движок вообще виден ядру |
| 9 | `\Bitrix\Crm\Integration\AI\BaasManager::isIgnored/setIgnored` | есть, публичные | `Main\Setup::ensureBaasIgnored()` |
| 10 | `TargetResolver` | цели — Deal и Lead | выбор сделки в тесте |
| 11 | `\Bitrix\Crm\Timeline\CommentEntry::create()`, `\Bitrix\Crm\Activity\Entity\ToDo` | есть; сигнатуры как в `Deal\Escalation` | эскалация |
| 12 | `\Bitrix\Crm\ActivityBindingTable`, `\Bitrix\Crm\History\Entity\DealStageHistoryTable` | есть, поля как в `Deal\ContextBuilder` | анализ сделок |
| 13 | `ThirdParty::hasQuality()` | audio виден только при наличии text-движка | регистрация обоих вместе |
| 14 | `\Bitrix\AI\Tuning\Manager::getItem()/save()`, `$item->setValue()`, `EventHandler::SETTINGS_FILL_ITEM_FROM_CALL_ENGINE_AUDIO_CODE` / `_TEXT_CODE` | есть; движок CRM берёт строго по коду из этой настройки | `Main\Setup::getEngineSelection()`, `selectEngines()` |
| 15 | одно задание Transcribe на дело (`callautostartstrategy.php:86-89`) | прежнее задание глушит автозапуск | каждый тест — новый звонок |

Расхождение — в отчёт, с оценкой: ломает ли оно модуль, и как (молча или
с ошибкой).

## Этап 3. Эндпоинт и движки

Цель: ядро видит наши движки, эндпоинт отвечает по контракту.

1. Настрой стенд: `docker compose exec -u www-data portal php
   /opt/stand/configure.php` — внешний адрес `http://portal`, провайдер
   `echo`, `Проверить и включить`. Ожидается: все строки OK, кроме `selected …`
   (код возврата 0 — их скрипт не считает),
   `engine audio` и `engine text` — `registered`, повторный запуск —
   `unchanged`. `selected audio/text` — FAIL «не выбран» или «выбран «X»»:
   прогон в настройки ИИ не пишет, это ожидаемо. Запиши, какой код там
   стоял по умолчанию на этой коробке (находка для отчёта).
2. Выбор движка — **со страницы настроек модуля**, как это сделает
   администратор: `/bitrix/admin/settings.php?mid=shef.toolsai`, вкладка
   «Движок», ссылка «Выбрать движок модуля» (браузер — Playwright, вход
   администратором). Ожидается: после редиректа «Готово: выбраны движки
   модуля», в строке — оба кода `sheftoolsai_*`, в
   `/settings/configs/?page=ai` — наши движки; повторный `configure.php` —
   `selected audio/text` «выбран наш». Проверь и отказ: ссылка без
   `sessid` и под пользователем без прав администратора ничего не меняет.
3. `SELECT ID, CODE, CATEGORY, COMPLETIONS_URL FROM b_ai_engine WHERE CODE
   LIKE 'sheftoolsai%';` — две строки, адрес с `?token=` (в отчёт — маской).
4. Контракт руками, **изнутри контейнера** (`docker compose exec portal bash`):
   - `curl -i http://portal/bitrix/tools/shef_toolsai_completions.php` → 200,
     `{"status":"ok"}`;
   - POST без токена → 403; с чужим токеном → 403;
   - POST с токеном и телом из `docs/01-engine-contract.md`, где
     `callbackUrl` ведёт на `http://evil.example/` → 400;
   - то же, но в `callbackUrl` нет `hash` → 400 `no_hash`;
   - POST с `prompt.file` = `http://169.254.169.254/latest/meta-data/` (или
     любой внутренний адрес стенда, кроме `portal`) → 202, но скачивание
     отказано: в журнале `ERROR`/`file_download`, провайдер не вызван
     (`/__stats`);
   - POST с токеном и корректным телом (колбэк на `http://portal/…` с
     выдуманным `hash`) → **202**, и время ответа: `curl -w
     '%{time_total}'` **меньше 1 секунды**. Это ключевая проверка для
     apache + mod_php: ядро ждёт ответ 5 секунд, и если соединение держится
     до конца обработки, задание упадёт по таймауту. Если время ≈ длительности
     обработки — это находка №1 с высшим приоритетом.
5. `ai`: `\Bitrix\AI\Engine::getByCategory('audio', \Bitrix\AI\Context::getFake())`
   (или то, что есть на твоём ядре) видит движок `sheftoolsai_audio`.

## Этап 4. Звонок → транскрипт (заглушка)

Цель: главный путь проходит без денег.

1. Лог автозапуска — `docs/04-runbook.md`, шаг 1: логгер
   `crm.Integration.AI` в `docker/www/bitrix/.settings_extra.php`, **но путь
   файла — `/var/www/sh_log/crm-ai.log`**, а не `/home/bitrix/sh_log/…` из
   runbook (это путь BitrixVM, в контейнере его нет).
2. Настройки автозапуска Копилота для воронки лидов и для основной воронки
   сделок: включить распознавание записи, входящие. **Сохранить явно**
   (гейт 3 и 4 в `docs/00-research.md`). Проверка —
   `cli/ai-call-autostart-diag.php`, раздел 3.
3. Соглашение Копилота на коробке (`AI_BOX_AGREEMENT`, гейт 8) должно быть
   принято **ответственным за лид/сделку** — в тесте это пользователь 1.
   Прими его в интерфейсе (всплывает при первом обращении к Копилоту) и
   запиши, где оно хранится на этом ядре.
4. Вебхук: `docker compose exec -u www-data portal php /opt/stand/webhook.php`
   (если не вышло — создай руками, см. шапку скрипта).
5. Звонок: `docker compose exec portal /opt/stand/test-call.sh
   <адрес вебхука> lead`, потом то же с `deal`. **Каждая проверка — новый
   звонок** (`test-call.sh` каждый раз заводит новый): на одно дело ядро
   ставит задание распознавания один раз, и прежнее задание, даже упавшее,
   глушит автозапуск (гейт 13). Упал — чини и звони заново, а не
   перевешивай запись на тот же звонок. Ответственный (пользователь 1) должен
   иметь право изменять дело звонка (гейт 12) — у администратора есть.
6. Ожидается, для каждого звонка, в пределах минуты:
   - в `crm-ai.log` — попытка автозапуска и операция транскрибации;
   - в таймлайне лида/сделки — текст `[заглушка shef.toolsai] Расшифровка
     записи…`;
   - на странице «ИИ: расход и остаток» (`/bitrix/admin/shef_toolsai_quota.php`)
     — строка `audio/echo/SUCCESS`, стоимость 0;
   - `SELECT * FROM shef_toolsai_usage ORDER BY ID DESC LIMIT 5;` —
     `JOB_HASH` заполнен, `STATUS = SUCCESS`.
7. Не появилось — **не чини наугад**:
   `docker compose exec -u www-data portal env ACTIVITY_ID=<id дела> php /var/www/html/bitrix/modules/shef.toolsai/cli/ai-call-autostart-diag.php` скажет, на каком
   гейте встало. Каждый гейт, который пришлось открыть, — в отчёт.
8. Если сценарий цепочки дальше транскрипта включён (резюме, заполнение
   полей) — проверь, что пришли запросы категории `text` (строки
   `text/echo/SUCCESS`) и что результат виден в карточке.

## Этап 5. OpenAI-совместимый провайдер (mock)

Цель: реальный протокол, расход в деньгах, ошибки провайдера.

1. `docker compose exec -u www-data portal env PROVIDER=openai php
   /opt/stand/configure.php`. Движки — `unchanged` (провайдер выбирается
   на каждый запрос, перерегистрация не нужна).
2. `curl http://localhost:8000/__reset`, звонок `test-call.sh … lead`.
3. Ожидается: в таймлайне — текст `[mock-openai] Менеджер: …`;

   `/v1/audio/transcriptions` с `file` типа `audio/mpeg`; в журнале —
   `audio/openai/SUCCESS`, `UNITS` ≈ длительности записи, стоимость > 0.
4. Ключ: `MOCK_API_KEY=test docker compose up -d mock-openai`, в
   настройках модуля ключ `wrong` (или `env API_KEY=wrong` для
   `configure.php`) →
   звонок → в журнале `ERROR` с кодом `provider_auth`, в тексте ошибки
   **нет** `wrong` (ключ маскируется); в карточке — ошибка Копилота, а не

5. Сбой: `curl -X POST 'http://localhost:8000/__fail?status=500&times=1'` →
   звонок → `ERROR`, `provider_unavailable`; следующий звонок — успех.
6. Недоступный провайдер: `API_baseurl` = `http://nowhere:9/v1` → ошибка
   `provider_unavailable`, эндпоинт при этом ответил 202 вовремя.

## Этап 6. Квота

1. `QUOTA=0.000001` в `configure.php` (одна микро-единица; env `QUOTA`) →
   звонок → в журнале `QUOTA_EXCEEDED`, провайдер **не** вызван
   (`/__stats` не вырос), ядру ушла ошибка `quota_exceeded`. Этот звонок
   автоматически уже не распознается (гейт 13) — так и должно быть; запиши,
   что видит пользователь в карточке.
2. Квота `0` → безлимит, звонок проходит.
3. Страница «ИИ: расход и остаток»: остаток, процент и разбивка сходятся с
   `SELECT CATEGORY, STATUS, COUNT(*), SUM(COST_MICRO) FROM
   shef_toolsai_usage GROUP BY 1, 2;` (стоимость на странице — в валюте,
   в базе — в микро-единицах).
4. Идемпотентность: повтори POST из этапа 3 с тем же `hash` дважды —
   во второй раз провайдер не вызван, строка в журнале одна.

## Этап 7. Анализ сделок

1. Сделка из этапа 4 (`deal`), сдвинь её «давность» на 20 дней:
   `UPDATE b_crm_act SET CREATED = NOW() - INTERVAL 20 DAY WHERE ID IN (…)`
   (только на стенде). 20 — с запасом: сделка «в работе», пока дел не было
   меньше `DEAL_idledays` (по умолчанию 3), а заглушки провайдера дают риск
   `дни × 5 + 10`, то есть 70 и выше — с 12 дней.
2. Настройки: «Анализ сделок» → включить, направление — основное, старший —
   пользователь 1, порог 70.
