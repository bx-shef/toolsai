# Что смотреть при обновлениях Битрикс24

Модуль `shef.toolsai` не правит ядро, но **опирается** на его поведение.
Обновление Битрикса может это поведение изменить — и почти всегда тихо.

Главный инструмент — `cli/core-api-guard.php`. Он проверяет все точки
опоры разом и печатает, что поехало. **Запускать после каждого обновления
платформы, до того как пустить людей работать.**

Скрипты едут вместе с модулем, в `cli/`:

```bash
cd /home/bitrix/www/bitrix/modules/shef.toolsai/cli
/usr/bin/php -f core-api-guard.php          # коротко
VERBOSE=1 /usr/bin/php -f core-api-guard.php # с пояснениями по каждой точке
```

Код возврата: `0` — всё на месте, `1` — есть расхождения.

---

## Шкала риска

| | Что значит |
|---|---|
| 🟥 **Критично** | сломается молча, распознавание просто перестанет работать |
| 🟧 **Заметно** | сломается с ошибкой в логе, чинится настройкой |
| 🟨 **Терпимо** | поменяется поведение, но не развалится |

## 🟥 Критичные точки опоры

### 1. `ThirdParty::checkLimits()` — на нём держится весь наш учёт

`ai/lib/Engine/ThirdParty.php:289-292`

```php
public function checkLimits(): bool
{
    return $this->item->getCode() === 'itsolutionru.gptconnector';
}
```

Сейчас лимитер включается только для одного приложения Маркета. Мы на это
рассчитываем: наш движок лимитов не знает, счёт ведём сами.

**Если Битрикс поменяет условие** (вернёт `true` всем, или заведёт список
кодов, или начнёт смотреть на `app_code`), лимитер включится и наши запросы
начнут упираться в `LIMIT_IS_EXCEEDED_*` — при том, что никаких пакетов BaaS
у портала нет. Распознавание встанет целиком.

**Как заметить:** guard читает тело метода через Reflection и сверяет с
эталонным хэшем. Плюс в журнале `shef_toolsai_usage` начнут появляться отказы,
которых мы не писали.

**Что делать:** либо переименовать наш движок так, чтобы он не попал под новое
условие, либо переключиться на `BaasManager::setIgnored(true)` уже для самого
лимитера — по обстоятельствам.

---

### 2. Статус-код `202` в ответе на completions

`ai/lib/Engine/ThirdParty.php:23,254`

```php
protected const HTTP_STATUS_OK = 202;
```

Если Битрикс сменит ожидаемый статус (на 200, или начнёт принимать диапазон
2xx), наш эндпоинт, отдающий строго 202, начнёт считаться сбойным.

**Как заметить:** guard читает константу через Reflection. В работе — все
задания падают сразу, с `Unknown error occurred with status 202`.

---

### 3. Маршруты колбэков

`ai/lib/QueueJob.php:39,42`

```
ai.controller.integration.thirdparty.callbackSuccess
ai.controller.integration.thirdparty.callbackError
```

Мы их не строим сами — берём готовые из `callbackUrl`/`errorCallbackUrl`
входящего запроса. Поэтому переименование маршрута **нас не сломает**, пока
Битрикс присылает актуальные URL.

🟥 становится только в одном случае: если вы где-то захардкодили путь. **Не
хардкодьте.** В модуле путь нигде не зашит — это проверяет guard.

---

### 4. Формат разбора успешного ответа

`ai/lib/Engine/ThirdParty.php:159-179` — `getResultFromRaw()`.

Сейчас: `{"result": ["текст"]}` -> `"текст"`. Если появится обязательная
обёртка (например, `{"data": {"result": …}}`), наш колбэк начнёт отдавать
мусор — а хуже того, `TranscribeCallRecording::canProceedToNextStep()`
(`transcribecallrecording.php:83-93`) увидит пустой `transcription` и **молча
оборвёт цепочку**, без ошибки.

**Как заметить:** задания в `b_crm_ai_queue` со статусом `SUCCESS`, но без
транскрипта в карточке. Guard сверяет сигнатуру метода.

---

### 5. Чтение `b_ai_engine` без проверки на модуль `bitrix24`

`ai/lib/Engine.php:130-148` — `loadThirdParty()`.

Наш движок жив ровно потому, что этот метод не спрашивает, коробка перед ним
или облако. Если Битрикс добавит туда гейт вроде `shouldUseB24()` (как уже
сделано для REST-регистрации в `ai/lib/Rest.php:28`), движок перестанет
подниматься, и `Engine::getByCategory('audio')` вернёт `null`.

**Как заметить:** guard регистрирует временный движок и проверяет, что
`Engine::getListAvailable('audio')` его видит.

**Что делать:** это фактически означает «коробкам своих движков нельзя».
Тогда путь один — конвейер целиком в своём модуле, мимо `\Bitrix\AI`: своё
событие на запись звонка, свой вызов провайдера, запись результата в
таймлайн. Провайдеры и учёт расхода модуля для этого годятся как есть.

---

### 5а. Связка «audio требует text»

`ai/lib/Engine/ThirdParty.php:297-310` — `hasQuality()`:

```php
// for audio category is required to exists any provider in text category
if ($this->getCategory() === $categoryAudio) {
    return !empty(Engine::getByCategory($categoryText, $this->context));
}
```

Наш audio-движок виден в CRM только пока жив text-движок. Если Битрикс
ужесточит условие (например, потребует text-движок **того же приложения** или
конкретное качество), audio выпадет из списка, выбор в настройках ИИ станет
пустым, и распознавание встанет без единой ошибки в интерфейсе.

**Как заметить:** guard, раздел «КРИТИЧНО 5», проверяет видимость движка
**с тем же фильтром качества**, что и CRM, плюс печатает, какой движок
выбран в настройке `crm_copilot_fill_item_from_call_engine_audio`.

## 🟧 Заметные точки

### 6. `BaasManager::isIgnored()` / `setIgnored()`

`crm/lib/integration/ai/baasmanager.php:104-121`, опция `crm::AI_IGNORE_BAAS`.

Публичные методы с внятными докблоками («It can be used if Baas is unavailable
for some reason») — вряд ли исчезнут, но **опция может сброситься** при
обновлении или переустановке модуля `crm`.

**Как заметить:** автозапуск перестал срабатывать, `AutoLauncher::isEnabled()`
вернул false. Это ловит `cli/ai-call-autostart-diag.php`.

**Что делать:** guard проверяет значение опции и предлагает вернуть. В модуле
есть идемпотентный `\Shef\ToolsAi\Main\Setup::ensureBaasIgnored()` — кнопка «Проверить и
включить» или `cli/setup.php`, прогоняйте после
обновлений.

---

### 7. Белый список целей `TargetResolver`

`crm/lib/Copilot/Pipeline/TargetResolver.php:18-21` — `private const ENTITY_TYPE_WHITELIST`.

Приватная константа, Битрикс меняет такое без предупреждения. Расширение
списка (добавят контакт/компанию) нам скорее на пользу. Сужение — сломает
часть звонков.

**Как заметить:** guard читает константу через Reflection и печатает состав.
Сравнивайте с прошлым прогоном.

---

### 8. Дефолтный набор автозапуска по зоне

`crm/lib/integration/ai/operation/autostart/fillfieldssettings/callchannelsettings.php:112-140`

Правило «вне зоны `ru` нет `Transcribe` в дефолте» — плавающее, Битрикс его
уже менял. Если у вас настройки воронок **сохранены явно**, дефолт не
применяется и вам всё равно. Если вы полагались на дефолт — поедет.

**Что делать:** всегда сохраняйте настройки автозапуска руками, даже если они
совпадают с дефолтом. Тогда эта точка перестаёт вас касаться вовсе.

### 9. Пороги пригодности аудио

`crm/lib/integration/ai/suitableaudioschecker.php:17-20` и список расширений
`crm/lib/Service/Timeline/Config.php:7`.

Константы приватные, но переопределяются опциями `crm`:
`ai_integration_audiofile_min_size`, `ai_integration_audiofile_max_size`,
`ai_integration_audio_min_call_time`, `ai_integration_audio_max_call_time`.

**Как заметить:** часть звонков перестала обрабатываться. Диагностика покажет
конкретную причину (`FILE_TOO_SMALL`, `CALL_TOO_SHORT` и т.д.).

---

### 10. Ключ кеша движков

`ai/lib/ThirdParty/Manager.php:14` — `private const CACHE_DIR = 'ai.thirdparty01'`.

Суффикс `01` Битрикс наращивает при смене формата кеша.

**Мы на него не завязаны:** регистрируем через `Manager::register()`, который
сбрасывает кеш сам (`Manager.php:43`). Именно поэтому в модуле **запрещено**
звать `ThirdPartyRegisterService` напрямую — пришлось бы хардкодить ключ.

Guard проверяет, что в коде модуля нет строки `ai.thirdparty`.

## 🟨 Терпимые точки

### 11. Состав тела запроса на completions

`ai/lib/Engine/ThirdParty.php:226-248`. Добавление новых ключей безвредно —
мы читаем только нужные. Переименование существующих (`prompt`, `category`,
`callbackUrl`) заметим сразу.

**Наш `Request::fromArray()` намеренно терпим:** любой отсутствующий ключ даёт
пустое значение, а не падение. Проверять содержательно — задача guard.

### 11а. Промпты текстовой цепочки CRM

Готовый `prompt` против сырого `payload_prompt_text`, коды
`summarize_transcript`/`extract_form_fields`/`call_scoring`, маркеры
(`original_message`, `fields`, `enum_fields_values`, `current_*`,
`transcript`, `criteria`, `language` названием) и разбор ответа
(`extractPayloadPrettifiedData`; поля — ключи по `NAME` и `comment`; оценка —
`call_review.criteria`, `scorecall.php:217-231`) —
[01-engine-contract.md](01-engine-contract.md), «text: резюме звонка и
заполнение полей». Поменялось — заполнение полей молча станет
`PAYLOAD_IS_EMPTY`, а оценка — пустой. После обновления crm — один звонок,
FillFields и ScoreCall в `b_crm_ai_queue` без ошибки. Обновление ai —
проверить, закрыты ли метками промпты в `ai/install/prompts/world.json`:
раскрыли — свои промпты можно выключить и сравнить.

### 11б. Чаты открытых линий (1.6.0)

Свои промпты узнают переписку по подписи «Имя [дата 'c']:» из
`OpenLine::getMessagesForCopilot()`: сменит CRM формат — переписка пойдёт с
нейтральной формулировкой, без правил про автоответы (не сломается). Своя
оценка чатов опирается на `b_imopenlines_session` (`START_ID`, `END_ID`,
`CLOSED`, `DATE_CLOSE`, `SPAM`), `b_im_message`, параметр сообщения `CLASS`
(`bx-messenger-content-item-ol-…`, `…-system`), дело `ASSOCIATED_ENTITY_ID` =
ID сессии и на подбор скрипта (`CopilotCallAssessmentController`,
`AssessmentClientTypeResolver`, `CallAssessmentItem`). Появится у CRM своя
оценка чатов — сравнить и решить, нужна ли модульная
([06-chats.md](06-chats.md)). После обновления crm/imopenlines —
`ACTIVITIES=<id> php -f cli/chat-assessment.php` на одном закрытом чате.

### 12. Таймаут 5 секунд

`ThirdParty.php:24`. Если Битрикс его увеличит — нам только легче. Если
уменьшит — эндпоинт должен успевать отвечать ещё быстрее. Держите обработчик
тонким: принял, положил в очередь, ответил.

### 13. `Config::getValue('public_url')`

`ai/lib/QueueJob.php:338` и `transcribecallrecording.php:180`. Значение
настраивается вручную и при обновлении не трогается, но проверять стоит —
от него зависят и колбэк, и загрузка записи.

## Регламент: что делать при обновлении платформы

Порядок ровно такой, по шагам.

**До обновления**

1. Снять эталон: `/usr/bin/php -f core-api-guard.php > /tmp/guard-before.txt`
2. Зафиксировать версию: `main`, `crm`, `ai`, `voximplant` — из
   `/bitrix/admin/update_system.php`.

**После обновления**

3. `/usr/bin/php -f core-api-guard.php > /tmp/guard-after.txt`
4. `diff /tmp/guard-before.txt /tmp/guard-after.txt` — любое расхождение
   разбираем до того, как пускать людей.
5. `/usr/bin/php -f ai-call-autostart-diag.php` — проверить, что цепочка
   автозапуска цела (особенно опция `AI_IGNORE_BAAS` и настройки воронок).
6. Тестовый звонок с записью -> убедиться, что транскрипт появился в карточке.
7. Страница «ИИ: расход и остаток» — сверить, что расход пишется;
   `/usr/bin/php -f cli/setup.php` — что движки и обход BaaS на месте.

**Отдельно проверить после обновления модуля `crm`**

- опция `crm::AI_IGNORE_BAAS` не сбросилась;
- опции `crm::ai_autostart_settings_*` на месте;
- логгер `crm.Integration.AI` в `.settings_extra.php` жив (файл обновлением
  не трогается, но проверить дёшево).

**Отдельно после обновления модуля `ai`**

- движок на месте: `SELECT * FROM b_ai_engine WHERE CODE LIKE 'sheftoolsai%'`;
- guard не ругается на пункты 1, 2, 4, 5.

## Если модуль `bitrix24` появится на портале

Такое бывает при смене редакции. Тогда меняется сразу многое:

| Что | Было (без `bitrix24`) | Станет |
|---|---|---|
| `check_limits` | `'N'` — промо-лимит выключен | `'Y'` — включится |
| `Bitrix24Manager::isFeatureEnabled()` | всегда `true` | по тарифу |
| `ai.engine.register` | метода нет | появится |
| `isSponsoredOperation` | не работает | заработает обнуление |
| `Daily::getMaximumUsage()` | 5 | по тарифному плану |

Наш движок при этом **продолжит работать** (он в таблице), но появится второй
счётчик — промо-лимит, который начнёт резать пользователей на 5 запросах в
сутки. Первым делом проверьте `/bitrix/admin/settings.php?mid=ai` ->
`check_limits`.

Guard печатает наличие модуля `bitrix24` отдельной строкой — именно ради
этого случая.

## Чего в модуле нет намеренно

Чтобы не создавать себе точек хрупкости:

- **нет правок ядра** — ни одной;
- **нет обращений к приватным API** — кроме чтения констант в guard, и это
  диагностика, а не рантайм;
- **нет захардкоженных URL колбэков** — берём из входящего запроса;
- **нет своей копии `b_ai_usage`** — мы её не трогаем, ведём свою таблицу;
- **нет подписки на события модуля `ai`** — точек входа и так достаточно.
