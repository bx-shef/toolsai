# Промпт: есть ли в ядре очередь повторов для распознавания звонков

Готовый промпт для ИИ-агента с доступом к **коробке Битрикс24** (ssh или
стенд из [agent-docker-test.md](agent-docker-test.md)). Задача — разведка, не
правка: ничего в ядре и в модуле не менять.

Зачем. Гейт 13 из [00-research.md](00-research.md): на одно дело звонка CRM
ставит задание распознавания **один раз**. Если наш движок ответил ошибкой
(квота, провайдер недоступен, запись не скачалась), автозапуск на этом деле
больше не срабатывает, а автоматический повтор — ровно один. Звонок остаётся
без расшифровки навсегда, пока кто-то не нажмёт вручную. Своей очереди
повторов у модуля нет. Прежде чем писать свою, надо понять, не сделал ли её
Битрикс в свежих версиях.

---

```text
Ты работаешь на коробке Битрикс24 (корень сайта — $DOCUMENT_ROOT, обычно
/home/bitrix/www; в docker-стенде — /var/www/html). Задача — РАЗВЕДКА: найти в
ядре механизм очереди/повторов для ИИ-заданий Копилота (распознавание записи
звонка и следующие шаги). Ничего не меняй в файлах ядра, в базе и в
настройках. Только читай и запускай SELECT.

Контекст. Сторонний ИИ-движок (модуль shef.toolsai) регистрируется через
\Bitrix\AI\ThirdParty\Manager::register(). Ядро шлёт ему POST, движок
отвечает 202 и позже шлёт колбэк с результатом или ошибкой. Известно по
разбору ядра (номера строк могут съехать — ищи файлы по имени в
bitrix/modules/crm, регистр каталогов бывает разный):
  - callautostartstrategy.php:86-89 (каталог .../autolauncher/) и
    abstractoperation.php:101-130 (crm/lib/Integration/AI/Operation) —
    на одно дело звонка задание TranscribeCallRecording ставится один раз;
    любое прежнее задание (даже с ошибкой) глушит автозапуск при обновлении
    дела, повтор — ровно один;
  - при ошибке звонок остаётся без расшифровки навсегда, если человек не
    нажмёт «Повторить» в карточке.
Нужно понять: есть ли в ЭТОЙ версии ядра очередь заданий или повторов,
которую сторонний движок может использовать, вместо того чтобы строить свою.

Шаги.

1. Версии. Запиши версии модулей main, ai, crm, voximplant, bizproc
   (install/version.php каждого) и дату последнего обновления.

2. Журнал обновлений. Открой /bitrix/admin/sysupdate_log.php?lang=ru (или
   прочитай то же из базы: SELECT * FROM b_updates_log ... — найди таблицу
   сам, если имя другое; или файлы /bitrix/updates/). Найди записи об
   обновлениях ai и crm за последние 12 месяцев и выпиши те, где в описании
   есть: очередь, queue, повтор, retry, перезапуск, restart, задани(е|я),
   job, фон, background, агент, воркер, worker, messenger, broker.
   Для каждой — версия модуля, дата, текст как есть.

3. Код ai. В bitrix/modules/ai найди (grep -rniE):
   "queue|retry|attempt|repeat|restart|backoff|Messenger|Broker".
   Особенно: lib/QueueJob*, lib/Model/QueueTable* (таблица b_ai_queue),
   lib/Engine/ThirdParty.php (что происходит с заданием, если колбэк с
   ошибкой или не пришёл вовсе — таймаут, TTL), lib/Controller/Tooling.php
   или то, что принимает колбэк. Ответь: хранит ли ai задание после ошибки,
   есть ли у него счётчик попыток, есть ли агент/cron, который
   перезапускает задания, и можно ли в колбэке сказать «повтори позже»
   (особый код ошибки, поле retry, HTTP-статус).

4. Код crm. В bitrix/modules/crm/lib/Integration/AI найди то же. Особенно:
   каталог autolauncher, Operation/abstractoperation.php (как считается
   «уже было задание», есть ли условие по статусу ошибки или по времени),
   JobRepository / Model/QueueTable / b_crm_ai_queue (или похожее), всё с
   "retry" / "restart" / "launchOperation" / "isManual". Ответь: где лежит
   признак «задание по делу уже было», можно ли его штатно сбросить, и что
   делает кнопка «Повторить» в карточке (какой контроллер, какой метод,
   какие проверки прав).

5. Общая очередь ядра. Проверь, есть ли в main брокер сообщений:
   bitrix/modules/main/lib/Messenger (Bitrix\Main\Messenger\*), таблица
   b_main_messenger_message или похожая, ключ "messenger" в
   /bitrix/.settings.php. Если есть — кто её использует из ai/crm, как
   регистрируется своя очередь и свой обработчик, есть ли повторы и
   задержка (delay) из коробки, что её крутит (агент, cron, воркер).

6. База. SELECT (только чтение) по найденным таблицам очередей и заданий:
   сколько строк, какие статусы, есть ли поля попыток/следующей попытки.
   Персональные данные (телефоны, текст, имена) в отчёт не переноси.

7. Проверка на стенде (только если это docker-стенд, НЕ боевой портал):
   сделай звонок, на который движок ответит ошибкой (в настройках модуля
   shef.toolsai поставь квоту 0.000001 — это даст quota_exceeded), и
   посмотри, что ядро сделало с заданием: записи в таблицах из шагов 3–5,
   лог crm.Integration.AI, повторилось ли задание само и когда.

Отчёт — markdown, ровно в этом виде:

## Версии
main / ai / crm / voximplant / bizproc, дата обновления.

## Журнал обновлений
таблица: модуль | версия | дата | текст записи (только относящиеся к делу).

## ai: что происходит с заданием после ошибки
файл:строка для каждого утверждения. Есть ли повтор, сколько попыток,
что его запускает, можно ли движку попросить повтор.

## crm: признак «уже было» и кнопка «Повторить»
файл:строка. Можно ли сбросить штатно; какой API у ручного повтора.

## Брокер сообщений main
есть / нет; если есть — как им воспользоваться стороннему модулю, с
файл:строка и минимальным примером регистрации очереди.

## Стенд (шаг 7)
что произошло с заданием по минутам.

## Вывод
Одно из трёх, с обоснованием:
  А) штатный повтор есть и сторонний движок может им пользоваться —
     как именно;
  Б) штатного повтора нет, но есть штатный API ручного повтора, который
     модуль может звать сам (агентом) — какой, с какими правами;
  В) ничего нет — модулю нужна своя очередь.

## Сомнения
что не удалось проверить и почему.

Каждое утверждение про код — с путём и номером строки. «Наверное»,
«скорее всего» без ссылки на строку — не годится: так и пиши «не нашёл».
```
