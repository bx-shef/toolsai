# Как ведётся этот репозиторий

Файл про процесс, а не про код. Опорные точки модуля, ловушки ядра и приёмочный
чек-лист — в [CLAUDE.md](CLAUDE.md), процедура проверки на портале —
в [docs/portal-check.md](docs/portal-check.md); раскладка репозитория —
в [docs/module-structure.md](docs/module-structure.md); сборка, CI и релиз —
в [docs/build-and-install.md](docs/build-and-install.md).

## Язык

Общаемся, документируем и комментируем код по-русски. Код — в стиле Битрикса:
табы, аллмановские скобки, `BX.create()` на фронте.

**Идентификаторы — по-английски.** Имена задач в workflow читает не человек, а
защита ветки: она сравнивает их строкой. Переименуете задачу `CI` — ruleset
перестанет её видеть, и в `main` начнёт уезжать непроверенное.

## Ветки и PR

В `main` не пушим — там стоит ruleset, он и не даст. Работа идёт в отдельной
ветке, изменения приезжают через PR.

Каждый шаг — отдельный PR. Не вываливать всё сразу: владелец должен успевать
смотреть.

**Ветвитесь от `main` и дожидайтесь мержа предыдущего PR.** В репозитории
разрешён только сквош-мерж, а он склеивает коммиты в новый и общую историю
теряет. Ветка, поднятая от другой ветки, после сквоша ловит конфликты в каждом
общем файле. Если так уже вышло — перебазируйте её на новый `main` и **сверьте
хеши деревьев**, а не глазами:

```bash
git rebase --onto origin/main <старая-база> <ветка>
git rev-parse <было>^{tree} <стало>^{tree}   # должны совпасть
```

## Перед тем как открыть PR

```bash
./build.sh --check
```

Ровно это же гоняет CI, так что красный CI после зелёного локального прогона
означает расхождение окружений, а не «моргнуло».

## Тело PR

Пишите «зачем» и «на что влияет», а не пересказ дифа — диф виден рядом.
Отдельным разделом — что проверить руками на портале: тестами рантайм Битрикса
не покрыть.

Нашли проблему в чужом PR — скажите до мержа, и с проверкой, а не с
предположением.

## Защита `main`

Целевая настройка — ruleset на ветке по умолчанию, bypass пуст. Владелец
включает её сам; до этого правила ниже — договорённость, а не запрет:

| правило | настройка |
|---|---|
| Require a pull request | апрувов **0** |
| Require status checks | ровно **`CI`** |
| Block force pushes | включено |
| Restrict deletions | включено |

**Апрувов ноль — это не небрежность.** В репозитории один человек, свой PR
апрувить нельзя, единица заперла бы репозиторий наглухо.

**Обязательная проверка ровно одна — `CI`.** Остальные задачи (`PHP 8.2`
… `PHP 8.5`, `Composer`, `Skills`, `Build`) — её зависимости. Добавите версию PHP в матрицу —
ruleset править не придётся.

## Мерж

Разрешён только **сквош**. Автоудаление влитой ветки включено.

Владелец разрешил агенту мержить: агент вливает сам то, в чём уверен и что
проверил, — после зелёного `CI`. Всё остальное — по прямой просьбе.

## После мержа

**Не пушьте в ветку после мержа — это заводит её заново.** Packagist делает
`dev`-версию из **каждой** ветки репозитория: содержимое любой забытой ветки
ставится через `composer require bxshef/toolsai:dev-имя-ветки`. Отключить это
нечем — ни настройкой пакета, ни полем в манифесте. Единственный рычаг: не
держать лишних веток.

После каждого мержа полезно убедиться, что на `origin` осталась одна ветка:

```bash
git ls-remote --heads origin
```

## Версия и релиз

**Версию поднимайте при каждом изменении поведения** — `install/version.php`,
поля `VERSION` и `VERSION_DATE`. Тег обязан совпадать с `VERSION`, иначе на
портал уедет архив, версия которого врёт, а версия — единственный способ
понять, что на портале стоит. Правку правила сопровождайте правкой теста и
документации в том же PR.

Записывайте изменение в `CHANGELOG.md` секцией `## <версия> — <дата>`: из неё
собираются примечания к релизу.

Выпуск — **Actions → Release → Run workflow** от `main`. Тег встанет сам, после
успешной сборки. Подробности и второй вход (пуш тега) —
в [docs/build-and-install.md](docs/build-and-install.md).

## Навыки агента — не здесь

`.claude/skills/` — копия из [bx-shef/options](https://github.com/bx-shef/options),
её раскладывает `sync.sh`. Навык линейки правят **в shef.options**, потом
раскладывают сюда:

```bash
../options/.claude/skills/sync.sh --to .
./build.sh --check
```

Правка копии на месте будет затёрта следующей раскладкой, а до неё — поймана:
`tests/skills_test.php` сверяет копию с её `MANIFEST`, задача `Skills` в CI — с
источником.

Исключение — **локальный** навык `shef-new-ai-provider`: он про сам
shef.toolsai, его источник здесь. После правки — `.claude/skills/sync.sh
--local` (пересобирает `LOCAL.MANIFEST`), иначе `--check` краснеет.

## Решения владельца

Решения владельца — решения, а не баги. Они записаны отдельным разделом
в [CLAUDE.md](CLAUDE.md) и не переигрываются без просьбы. Меняете правило —
правьте тест и документацию в том же PR.

## Репозиторий публичный

Значит, публичны и комментарии. Не пишите в файлы того, что предназначено
своим: внутренних обоснований, рамок разговора с заказчиком, ссылок на работу
по другим клиентам, адресов внутренних порталов.

Удаление потом не помогает: текст остаётся в истории git и в уже выпущенных
архивах. Force-push тоже не спасает — GitHub отдаёт старые коммиты по прямому
SHA, пока их не соберёт сборщик мусора, а запустить его может только поддержка.

Проверять надо **артефакт, а не свой диф**: скачать выпущенный архив,
распаковать и прогрепать целиком. Текст, вычищенный из документации, легко
остаётся в комментарии JS и уезжает в поставку.
